# M4 第一阶段设计分析（八部分）

> 范围：**只做第一阶段** —— `DeepSeek + 高德地图 + search_nearby + 酒店卡片`，
> 目标是让「汉中高铁站附近推荐酒店」跑通完整闭环。
>
> 本文是**动手前**的分析记录。TripContext（阶段二）、`get_route`（阶段三）、
> `website_food_search`（阶段四）在本文中只出现"位置在哪、为什么现在不做"，
> 不写实现细节 —— 否则会变成"设计了一堆用不上的东西"。
>
> **补记（2026-09-27）**：阶段二、三都已做，但**阶段三的口径与本文不同** ——
> 本文设想 `get_route` 用 `selected_attraction` 当终点（即"酒店 → 景点"这一段），
> 实际做成了**通用两点驾车**（起终点取自用户原话），与 `trip_context` 没有打通。
> 本文下面的字段表**保持原样**，因为它是"当时的设计意图"的记录；
> 差异表见 `docs/模块划分与依赖.md`「阶段三的落地差异」与

## 三、哪些必须保持不动（红线）

1. **`/ai/qa` 的对外契约不动。** `meta.route` / `meta.mode` / `meta.sources` /
   `delta` / `done` 的含义与字段名一个都不改。理由：M3 已有验收记录与前端分支，
   动它等于把已验收的东西重新变成"待验收"。
2. **`KbStore` 不动。** 不为了 Agent 加"按 POI 检索"这类方法 —— 那是 `tools.py` 的事。
3. **SSE 不删、不改协议方向。** 不引入 WebSocket，不改成一次性 JSON。
4. **`AMAP_KEY` 不出后端。** 前端、Java 都不持有高德密钥；高德只在 Python 侧被调用。
5. **DeepSeek 不生成 POI。** 酒店名/地址/经纬度/距离/电话只能来自高德返回，
   模型只能"引用 + 组织语言"。
6. **两类美食不混。** 第一阶段不碰网站自有商品，`website_food_search` 留到阶段四。
7. **不做推荐算法。** 排序用高德的 `sortrule=distance`，不自研打分。
8. **不加 `city_code` 到任何"不该随重启消失"的表。** 第一阶段本来就不建表。

## 四、游客账号上下文放哪

分三层，**现阶段只落地第一层的"可读取"，不落地"持久化"**：

```
User（游客账号）
  └── Trip（一次旅行）              ← 阶段二才建表
        └── TripContext（上下文）   ← 阶段二才持久化
```

- **账号**：沿用 M8 的 `app_user`。它**不带 `city_code`**，所以重启不会被重灌 ——
  这正是"账号能跨会话存在"的前提。
- **`TripContext` 放哪**：**不放 Redis，也不放前端 localStorage。**
  理由：它是"AI 记住的旅行事实"，必须是**服务端权威**。放前端的话，
  用户改一下 localStorage 就能让 AI 相信他住在另一个酒店，而 AI 又拿这个经纬度去查附近 ——
  错的是"信任了一个不该信任的来源"。
- **第一阶段怎么做**：**先不建表，也不加参数。** 第一阶段的闭环（问附近酒店）
  **不需要上下文** —— 用户问什么，调度器就查什么。

  **刻意不在 `AgentService.stream` 上预留一个 `context=None` 参数**，
  尽管那样"看起来为以后留了口子"。理由：一个被接收但被忽略的参数，
  会让 `stream(question, context=ctx)` 这样的调用点**看起来像上下文已经生效**。
  等阶段二真接上时，最先要排查的就是"为什么传了上下文却没用" ——
  而这本可以由"根本传不进去"来避免（编译期就发现，而不是运行期猜）。

  阶段二的改法是：`stream(question, context=...)` + `_decide` 把上下文摘要
  拼进调度器消息，**改的是 `stream` 内部与它的调用方**，
  工具层与 `amap.py` 完全不用动 —— 因为"附近搜索"的入参本来就是坐标，
  上下文只是**坐标的来源**变了。

## 五、TripContext 设计（阶段二落地，此处只定形状）

字段按用户给定，**只加一个 `updated_at`**（用于判断"这个上下文是不是过期的"）：

| 字段 | 类型 | 来源 | 说明 |
|---|---|---|---|
| `user_id` | int | M8 登录态 | 上下文归属，不信任前端传值 |
| `trip_id` | str | 服务端生成 | 例 `2026-hanzhong-001` |
| `destination` | str | 首次对话/数据包 | 默认 `汉中` |
| `current_location` | `{lng, lat, name}` | 高德逆地理 或 用户选择 | 有它才能"我附近" |
| `selected_hotel` | `{poi_id, name, address, longitude, latitude, source}` | 用户点「选择酒店」 | **必须存坐标**，只存名字则"附近"无从算起 |
| `hotel_booking_status` | enum | 状态机 | `not_booked` / `external_pending` / `booked` / `cancelled` |
| `selected_attraction` | `{poi_id, name, lng, lat}` | 同上 | **原写**"阶段三 `get_route` 的起点/终点"；**实际** `get_route` 没读这个字段（起终点取自用户原话），见本文头部补记 |
| `selected_restaurant` | `{poi_id, name, lng, lat}` | 同上 | |
| `planned_attractions` | list | 行程规划 | 阶段五 |
| `visited_attractions` | list | 打卡 | 阶段五 |
| `food_preferences` | list[str] | 对话中抽取 | |
| `travel_start_date` / `travel_end_date` | date | 用户输入 | |
| `updated_at` | datetime | 服务端 | 过期判定 |

**两条设计约束：**

1. **`booking_status` 只做状态，不做订单。** 这一版不存在 `hotel_booking` 表。
   之所以现在就定义这个枚举，是为了让"去美团预订"这个跳转**有地方记状态**
   （点了跳转 → `external_pending`），而不是等以后加预订功能时再回头改数据结构。
2. **`source: "amap"` 必须存。** 以后如果换成自采数据或别的地图，
   历史上下文里能分清"这个坐标当时是哪来的"。

## 六、高德代码放哪

**只放 `server-ai/app/amap.py` 一个文件**，且**只被 `tools.py` 调用**。

```
main.py  ──创建──▶  AmapClient（单例，挂 app.state）
                        ▲
                        │ 只用接口
                    tools.py  ──▶  agent.py
```

**为什么不让 `agent.py` 直接调高德**：调度器是"选工具的人"，
如果它还能直接查地图，那"有没有经过工具层"就说不清了 ——
答辩时无法证明"数据来自工具"。中间隔一层 `tools.py`，
`ToolResult.cards` 就是"数据确实来自高德"的证据。

**三种静默失败必须在 `amap.py` 里挡住**（官方文档原话驱动，不是猜的）：

1. **字段为空时返回 `[]` 而不是 `""`。** 官方："部分返回值当返回值存在时，
   将以字符串类型返回；当返回值不存在时，则以数组类型返回。"
   → 所有取值走 `_s()`，把 `[]`/`None`/`dict` 一律归一成 `""`。
   **不处理的话 `tel` 为空就 `AttributeError`，而"这家店没电话"是正常情况。**
2. **`status` 是字符串 `"1"`/`"0"`。** `status=0` 必须**抛 `AmapError` 并带上 `infocode`**，
   否则"这里没有酒店"和"你的 key 无效"在日志里长得一模一样，排查要花一晚上。
3. **坐标是 `"经度,纬度"` 字符串，经度在前。** `_split_location` 统一按经度在前解析，
   并**四舍五入到 6 位小数**（高德给的就是 6 位，多存没意义）。

**另两个必须显式传的参数：**

- `citylimit=true`：不传的话"汉中博物馆"会返回外地的同名 POI。
- `extensions=all`：不传就拿不到 `tel` / `adname` / `business_area` / `biz_ext` / `photos`，
  而酒店卡片要显示电话和区县。
- `radius` 上限 50000（默认 5000）；`offset` 官方"强烈建议不超过 25"。
  超出不报错，是**静默按上限截断** —— 属于第 1 类静默失败，所以在客户端里钳位。

### 关键设计决定与理由

**A. 为什么用自写 JSON 路由，不用原生 `tool_calls`？**

1. **决策不需要流式。** 它是短输出（一行 JSON），而原生 `tool_calls` 的流式返回
   要按 `index` 累加 delta 再拼，各家实现细节不一致，拼错的表现是"参数偶发丢失"——
   这种 bug 最难查。
2. **可移植。** `.env` 允许换通义 / Kimi / Ollama。自定 JSON 协议只依赖
   "模型会输出 JSON"这一件事，不用为每个厂商重验一遍 `tool_calls` 语义。
3. **可解释。** 决策原文进日志（`[Agent] 决策 tool=... args=... raw=...`）。
   答辩被问"它真的调工具了吗"，能直接甩日志，而不是"应该调了吧"。

**B. 为什么 `ToolResult` 有两个输出（`text` + `cards`）？**

模型的输出是自然语言，而卡片的字段必须**逐字准确**（用户要照着电话打过去）。
让模型把结构化数据转述一遍、前端再解析回来 —— 中间任何一步出错都是"酒店名少个字"。
所以：**给模型的走 `text`（可以只引用），给前端的走 `cards`（逐字来自高德）。**

**C. 为什么不缓存 Agent 的答案？**

M3 的 `AnswerCache` 不能复用：答案依赖**实时**高德数据。
回放一份缓存酒店列表 = 用户照着打电话，那边说"我们早搬走了"。
所以 Agent 的**离线路径**是**规则兜底**（回退 `knowledge_search` + `extractive_answer`），
不是"回放上次答案"。

**D. 为什么新开 `/ai/agent` 而不是扩展 `/ai/qa`？**

`/ai/qa` 的契约是"知识问答"：`meta.route` / `meta.sources` 描述的是检索行为。
Agent 的 `meta` 里是 `tools` / `amap`，`done` 里是 `tool` —— 两套语义塞进一个端点，
前端每处都要判断"这次有没有 tool 字段"。**分开的代价是多一个端点，混在一起的代价是
M3 已验收的契约被污染。**

**E. 离线时的行为。**
