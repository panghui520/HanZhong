## 0. 先说三句实话（写在方案最前面）

**第一，农产品方向是对的，但成败取决于一条设计红线。**
如果农产品是"一个商品列表 + 购物车"，那它就是商城，评委一句"你这和文旅有什么关系"就能打死。
如果农产品**只能从"乡村体验"长出来**——每个产品必须挂靠一个体验活动与产地乡村点，那么它就是文旅消费链的延伸节点。本方案全部设计围绕这条红线。

**第二，创新方向 C（多业态统一数据模型）应当降级。**
统一建模是**工程基础**，不是创新点。评委会问"统一数据模型解决了什么别人解决不了的问题"，答不上来就丢分。我把它移到"技术支撑"章节，创新点只保留 3 个能把故事讲圆的。

**第三，NL2SQL（管理者自然语言问数）不要进 P0。**
让 LLM 直接写 SQL，在 32 天单人项目里翻车概率极高（错表、注入、慢查询、答非所问）。P0 只做"固定指标卡 + AI 解读按钮"；NL2SQL 放 P1，且必须加白名单校验。

## 1. 最终项目名称

**主名称**：汉游智脑（HanYou Brain）
**完整标题**：汉游智脑——面向智慧文旅与乡村振兴的文旅消费链智能延伸与管控平台

## 2. 一句话定位

> **把游客的一次到访，变成一条持续的乡村消费链。**

不是旅游聊天机器人，不是农产品商城，不是数据大屏。
它做的是一件事：**用 AI 把"景区超载的溢出客流"导向乡村，并让这次乡村体验在游客回家之后仍然产生消费。**

## 3. 核心痛点（4 条，每条都要能在答辩时举出证据）

| # | 痛点 | 现状 | 本平台做法 |
|---|---|---|---|
| 1 | **冷热失衡** | 热门景区节假日超载、体验差；同城的乡村资源闲置 | 承载力联动的**智能分流**：识别超载 → 匹配周边乡村 → 改写行程 |
| 2 | **旅游消费"一次性"** | 游客离开目的地，消费关系即刻归零，乡村产业拿不到长期客源 | **体验锚点 + 离境复购**：把体验与产品绑定，离境后仍可复购 |
| 3 | **业态数据割裂** | 景区、餐饮、住宿、乡村、农特产分属不同系统，无法联动分析 | **统一文旅资源网络**（一张 POI 表 + 一张关系表承载全部业态） |
| 4 | **管控靠经验** | 管理者看报表、拍脑袋，异常发现滞后 | **规则引擎 + 多智能体**：阈值自动发现 → LLM 归因 → 工单闭环 |

## 4. 核心用户

- **游客**（来汉中/周边的中短途游客，含带老人小孩的家庭客）—— 用游客端
- **文旅管理者**（市/县文旅局、运营公司）—— 用管理端
- **乡村经营主体**（民宿、农家乐、合作社、农特产商户）—— 被平台纳管与曝光（**不给独立登录端**，P3）

## 5. 核心业务闭环（V2.0）

```
游客需求（天数/预算/人群/兴趣/步行意愿）
   ↓ ① AI 行程规划（LangGraph 多智能体）
多业态资源协同（景区 + 餐饮 + 住宿 + 交通 + 乡村体验）
   ↓ ② 承载力联动分流（景区超载 → 乡村点替代）
游客到访乡村 → 体验（采茶/采摘/民宿/非遗）
   ↓ ③ 体验锚点触发
特色农产品认知与首次购买（产品挂靠体验 + 产地）
   ↓ ④ 游客离境
"我的足迹"沉淀 → ⑤ 离境复购推荐 → 再次购买
   ↓ ⑥ 全链路数据沉淀（客流/消费/评价/复购）
管理端 AI 分析 → 风险事件 → 工单 → 处置反馈
   ↓ ⑦ 反馈优化资源匹配权重
回到 ①
```

**闭环成立的关键**：②⑤ 两步是别人没有的，①⑥⑦ 是别人也有的。差异化只在 ② 和 ⑤。

## 7. 多业态融合模型（V2.0）

### 7.1 统一资源网络（技术表达）

所有业态是**同一张图的节点**，不是 6 个独立模块：

```
                        ┌──────────────┐
                        │    visitor   │ 游客
                        └──────┬───────┘
                               │ 到访/足迹
        ┌──────────┬───────────┼───────────┬──────────┐
        ▼          ▼           ▼           ▼          ▼
    ┌───────┐  ┌───────┐  ┌───────┐  ┌───────┐  ┌────────┐
    │ SCENIC│  │ FOOD  │  │LODGING│  │TRANSP.│  │RURAL_  │
    │  景区 │  │ 餐饮  │  │ 住宿  │  │ 交通  │  │ SPOT   │
    └───┬───┘  └───┬───┘  └───┬───┘  └───┬───┘  └───┬────┘
        └──── poi_relation（邻近/配套/同村/分流）────┘
                               │
                     ┌─────────▼──────────┐
                     │    experience      │ 乡村体验项目
                     │ 采茶/采摘/民宿/非遗 │
                     └─────────┬──────────┘
                               │ 体验锚点（产品只能从这里长出）
                     ┌─────────▼──────────┐
                     │      product       │ 特色农产品/文创
                     └─────────┬──────────┘
                               │ 离境复购
                     ┌─────────▼──────────┐
                     │  order(REPURCHASE) │
                     └────────────────────┘
```

### 7.2 三条设计铁律（防止跑偏成电商）

1. **产品必须挂靠 `experience_id` 或产地 `poi_id`**（至少一项非空，数据库层加校验）。没有体验来源的产品不允许入库。
2. **产品详情页第一屏是"这个产品从哪次体验来"**，不是价格。展示：产地乡村 → 关联体验 → 村里谁在做 → 产品故事。
3. **不设独立的"商城"一级导航**。农产品入口只有三处：乡村点详情页、「我的足迹」、AI 助手推荐。

### 7.3 管理端融合指标（一张大屏看完）

- 客流侧：实时到访、承载力占用率、热度 Top10
- 乡村侧：乡村到访占比、**分流贡献量**（来自分流工单的到访数）
- 消费侧：农产品销量/销售额、**体验→购买转化率**、**离境复购率**
- 评价侧：负面评价率、评价情感趋势
- 风险侧：未处置事件数、平均处置时长

## 10. 农产品模块的定位（重点）

### 10.1 它是什么
**农产品 = 乡村体验的可带走形态。** 游客在村里采了茶，那罐茶就是这次体验的延续；回家喝完了想再买，就是复购。

### 10.2 必须做 / 可模拟 / 坚决不做

**必须做（P0）**
- 产品展示与分类（分类用字典，不建复杂类目树）
- 产品详情（**首屏是体验溯源**，其次是规格/价格/故事）
- 产品 ↔ 乡村点 ↔ 体验的三者关联
- 旅行中的推荐（在乡村详情页 + AI 助手中）
- 简单购物车（一张表，不做促销、不做优惠券）
- 模拟下单（生成订单号，状态直接置为"已支付（模拟）"）
- 历史购买与**一键复购**
- 「我的足迹」→ 离境复购推荐（AI）

**可模拟（P0 内用假数据）**
- 支付：跳过，订单状态直接写 `SIM_PAID`
- 物流：只存"已发货/已签收"两个状态字段，无轨迹
- 库存：一个 `stock` 整数字段，下单减一，不做锁库存/预警
- 结算/商家分账：完全不做

**坚决不做（P3）**
真实支付接入、物流轨迹、完整电商后台、供应链、多规格 SKU、优惠券/满减/秒杀、购物车合并结算、评价追评、售后退款流程、商家独立后台与登录、推荐算法训练

> 一旦有人（包括你自己）提出"要不要加个优惠券"，答：**不做，那是电商。**

## 11. RAG 设计

**两个 Chroma collection**

| collection | 语料内容 | 用途 |
|---|---|---|
| `kb_city` | 汉中历史文化、景区介绍、美食、路线、住宿、交通、文旅政策、乡村故事 | 问答 + 行程规划知识支撑 |
| `kb_product` | 农特产/文创的产品故事、产地、工艺、季节、食用与保存 | 产品推荐 + 问答 |

**链路**
```
CityPack/docs/*.md → 切分(500字/overlap 50) → Embedding → Chroma
检索：向量 top-k=5（HyDE/query rewrite 可选 P2）→ 重排(P2) → 拼 context → LLM
```
> 实际实现（M3，2026-09-26）：检索为**向量召回 ∪ BM25 召回 → RRF 融合排序**（不依赖重排模型）；
> 并且 **LLM 是回答模型、知识库只是增强来源** —— 按问题性质分三条链路：
> 涉及汉中的走 `rag`/`constrained`（检索 → 【资料】交给模型），
> 与汉中无关的走 `general`（**不检索**，直接由模型回答）。

**硬要求**：**涉及本地知识的回答必须带 `source_url` 引用**，前端展示"来源"角标。
与汉中无关的问题（问系统自身、通用概念）不检索知识库，因此**也不署名来源** ——
"**没用上的资料不署名**"比"每条都挂一个来源"更经得起核对。
**意义**：这是"可信文旅知识"的实体化，答辩时一句
"我们**每一条涉及汉中事实的回答**都可溯源、可审核"能直接回应"LLM 幻觉"质疑；
而"知识库没写过就不许编造本地事实"由**提示词**约束（不是靠拒答），
所以既不放过幻觉，也不会把"你是 AI 吗"这种模型本来就能答的问题一起拒掉。

**Embedding**：优先用与 LLM 同厂商的 OpenAI 兼容 embedding 接口；本地 BGE 系列作为 P1 备选。
**评测**：自建 40 条 QA 对，测 Recall@5 与答案忠实度（人工 + LLM-as-judge），结果写进项目说明书。

## 12. Agent 设计（6 个领域 Agent + 1 个运营 Agent）

### 12.1 游客侧 6 个领域 Agent（在 `retrieve` 节点内 `asyncio.gather` 并发）

| Agent | 输入 | 工具 | 输出 |
|---|---|---|---|
| `scenic_agent` | 兴趣/人群/步行意愿 | 检索 POI(SCENIC)、查客流与承载力 | 候选景区 + 拥挤提示 |
| `food_agent` | 兴趣/预算/位置 | 检索 POI(FOOD) | 候选餐饮 |
| `lodging_agent` | 预算/人群 | 检索 POI(LODGING) | 候选住宿 |
| `transport_agent` | 起终点/时间 | 检索 POI(TRANSPORT) + 距离矩阵 | 通勤耗时/方式 |
| `rural_agent` | 兴趣/**承载力溢出** | 检索 POI(RURAL_SPOT) + experience | 候选乡村点与体验 |
| `product_agent` | **体验锚点 + 足迹 + 兴趣** | 检索 product（带 experience_id 过滤） | 候选农特产与推荐理由 |

> **设计要点**：`product_agent` 的输入不是"用户想买什么"，而是"**用户体验过什么**"。这就是"不是电商"的技术证据。

### 12.2 管理侧 1 个运营 Agent
`ops_agent`：输入结构化指标（客流、承载、销量、转化、复购、情感），输出三段式：
1. 发生了什么（数据事实）
2. 为什么（归因假设，需标注为假设）
3. 建议做什么（可执行的 2–3 条，可直接转成工单）

## 13. LangGraph 设计（V2.0）

```
START
  ↓
parse          规则+LLM 抽取结构化约束（days/budget/party/interests/walk_tol）
  ↓
route ── Command 路由 ──┬──→ qa ────────────────────────→ END      # 知识问答
                        │
                        ├──→ retrieve ──→ synthesize ──→ critique ──┬─(retry<2 且校验不过)→ 回 synthesize
                        │      ↑ 6 个领域 Agent 并发                 │
                        │                                           └─→ END
                        │
                        └──→ footprint ──→ match ──────────────────→ END   # 离境复购推荐
```

**State**
```python
class PlanState(TypedDict):
    query, city, days, budget, party, interests, walk_tol
    kb_hits                                     # RAG 召回
    attractions, foods, hotels, transports, rural, products
    itinerary, critique, retry
    footprint                                   # 足迹/历史订单（复购分支用）
```

**节点说明**
- `parse`：LLM 结构化抽取（`with_structured_output`），失败则回落规则解析
- `route`：`Command(goto=...)` 三分支
- `retrieve`：**单节点内 `asyncio.gather` 并发 6 个 Agent**，不要把 Agent 拆成图节点——图保持扁平才好调
- `synthesize`：生成逐日行程
- `critique`：**规则校验**（超预算 / 超天数 / 步行量超标 / 开放时间冲突 / **景区超载**），条件边回退，最多 2 次
- `footprint` → `match`：读足迹与历史订单 → `product_agent` 匹配 → 生成复购推荐与理由

**关于「乡村分流」节点的诚实建议**
- **P0 做法**：分流逻辑写在 `synthesize` 的 prompt 与 `critique` 规则里（"若某景区承载力 >80%，用 `rural_agent` 给出的乡村点替换"）。能跑通、能演示、调试简单。
- **P1 做法**：把 `divert` 抽成显式图节点（`critique` → `divert` → `synthesize`），图上更好看、答辩更好讲。
- **先做 P0，跑通后再升级为 P1。** 不要一上来就做两条回边。

**必须自己写**：State 定义、`route` 条件边、`critique` 规则、6 个 Agent 的 prompt。
**AI 工具模板化生成**：LLM 调用、Chroma 检索、JSON 解析、并发封装。

## 14. AI 运营分析

**三段式架构（确定性 → 概率性，不可颠倒）**

1. **规则引擎（Java，确定性）**：6 条规则扫 `poi_visit_stats` / `feedback` / `order_item`，命中即写 `risk_event`。这部分**不用 LLM**，保证稳定可解释。
2. **LLM 归因（Python）**：把结构化指标 + 事件喂给 `ops_agent`，输出三段式。LLM **只做解释与建议，不做判定**。
3. **工单闭环（Java）**：建议 → 一键转工单 → 处置反馈 → 事件关闭 → 数据回流影响下一轮推荐权重。
   （**M5 已落地到「事件关闭」**；末段"数据回流影响下一轮推荐权重"未实现，见 §15 末的「M5 落地差异」）

**P0 交互**：指标卡 + 「让 AI 解读」按钮（点哪个指标就解读哪个）。
**P1 交互**：NL2SQL 自然语言问数 —— 仅限 **3 张宽表白名单**、只允许 SELECT、强制 LIMIT 200、只读数据库账号。

**M7 落地差异（2026-09-27，实现已验收，详见 `docs/验收记录-M7.md`）**

上面这三段架构与两级交互是**设计口径**，实现时在**四处**收敛 + **一处未实现**：

| 设计稿 | 实现 | 为什么 |
|---|---|---|
| §14.2「把结构化指标 + **事件**喂给 **`ops_agent`**」 | **没有独立的 `ops_agent`**。`server-ai/app/ops_analysis.py` 由端点直接调用，输入是**按关注点切好的指标**（4–12 个字段），不喂 `risk_event` 明细以外的"事件" | ① 这里是**单次调用**（一次请求一次补全），套一个 "agent" 的名字只是包装，答辩时会被追问"它自己决定做什么了吗"；② 送全量指标会把输出摊薄成一句一段的泛泛之谈，模型还会挑它爱讲的那块讲（点了"销售"却拿到讲客流的分析）。所以**一次只解读一组**，切片在 `slice_metrics` |
| §14 P0 交互「**指标卡** + 「让 AI 解读」按钮」 | 按钮在**解读面板内**（6 个维度切换），不在 KPI 卡上 | 点 KPI 卡上的按钮、结果却出现在屏幕另一端，是自找的困惑。而且 KPI 卡 5 张、可解读维度 6 个（"冷热失衡"没有对应的 KPI 卡），本来也做不成一一对应 |
| §14 P1 交互「NL2SQL 自然语言问数」 | **未实现** | P1 本身是"有余力再做"。且它与本项目的边界相冲：NL2SQL 要连业务库、要放开任意 SQL，而"Python 侧无状态、**不连业务库**"是 M3 起定下的分工。**答辩时不要讲这一句** |
| §16 内部接口表 `POST /ai/analyze/ops`：请求 `{metrics}`、响应 `{summary, insights}` | 请求 `{focus, metrics}`；响应 `{focus, focus_label, mode, model, generated_at, stale, note, period_label, synthetic, sections[], basis[]}` | `{summary, insights}` 装不下三样**界面必须显示**的东西：**模式**（真调了模型 / 离线回放 / 暂不可用）、**依据**（由代码算，可对着面板核）、**是否过期**（`stale`）。三者缺任一，这一块就只是不可核对的"AI 说的" |
| §16 可靠性「Python 不可用时 Java 返回**缓存行程或规则模板**」 | M7 **不回落成模板文案**：取不到就是 `mode=unavailable` + 一句原因，界面照实说明 | 驾驶舱原来那段"运营建议"**就是**模板，M7 把它换掉的全部意义在于"这一段真的有模型参与"。再回落成模板，界面会在不知情的情况下把模板当 AI 解读展示 —— 那正是要消除的东西。缓存回放时也一样：`mode=cache`、`stale` 标出数据是否已换，**宁可口径说清楚，也不要让一段过期数字冒充当前解读** |

其余部分（**三段式**、判定与解释分离、模型只解释不判定、指标由服务端算好）
**按设计稿落地，没有偏离**。

> **路径说明**：Java 对外的端点是 `POST /api/admin/ops/analyze`，不是 `/api/ai/analyze/ops`。
> 原因是 `/api/ai/**` 整段 permitAll（问答对游客开放），而这个接口返回的是运营数据的解读。
> **Python 侧的端点仍叫 `/ai/analyze/ops`**，所以 §16 的内部接口表不用改路径。

## 15. 风险与乡村分流机制

| # | 规则 | 触发条件 | 动作 |
|---|---|---|---|
| 1 | 客流超载 | 当日到访 ≥ 承载力 80% / 100% | 预警 / 一级事件 |
| 2 | 差评激增 | 24h 负面评价率 > 30% 且样本 ≥ 5 | 服务质量工单 |
| 3 | 热度突变 | 7 日环比增幅 > 80% | 关注 + 承载力复核 |
| 4 | **乡村闲置（核心）** | 主景区承载 > 80% **且** 周边乡村点承载 < 20% | **分流工单**：推送乡村点、下发推荐位、改写后续行程 |
| 5 | **产品转化低（核心）** | 乡村到访高但体验→购买转化率 < 阈值 | **曝光/组合建议工单**：调整 product_agent 权重 |
| 6 | 复购衰减 | 某产品 30 日复购率环比下降 > 40% | 触达建议工单 |

**分流链路（这是创新点 A 的实体）**
```
规则4 命中 → risk_event → work_order(type=DIVERSION)
  → ① 管理端：一键下发推荐位
  → ② 游客端：AI 行程规划时 rural_agent 权重上调，生成"乡村替代方案"
  → ③ 数据回流：分流产生的到访写入 trip_checkin(source=DIVERSION)，大屏显示"分流贡献量"
```

**M5 落地差异（2026-09-27，实现已验收，详见 `docs/验收记录-M5.md`）**

上面这张规则表与链路是**设计口径**，实现时在**七处**收敛，改的是口径不是能力，逐条记在这里：

| 设计稿 | 实现 | 为什么 |
|---|---|---|
| §14.1「6 条规则扫 `poi_visit_stats` / **`feedback`** / **`order_item`**」 | **`feedback` 表不存在；`order_item` 也没扫。** 六条规则只读 **`poi_visit_stats` + `poi`** 两张表 —— 评价、体验参与、购买、复购四类数字都是 `poi_visit_stats` 上的**列**（合成数据），不是从订单表实时聚合的 | ① 一条规则只要"条数"这种整数，为它单开 `feedback` 表违反 §16 自己定的"能聚合就不建表"；② 让规则引擎去读 M6 的订单表，会把 M5 绑死在 M6 的表结构上（换城市、改订单字段都要动 M5），而订单侧的口径变化还会**静默改变历史风险事件的含义** |
| §15 规则 6「某**产品** 30 日复购率环比下降 > 40%」 | 收敛为某**乡村点**复购量环比下降 | 本模块的统计表是"资源点 × 天"；产品级日度复购要再建一张表，与"19 张表别再加"冲突（当时口径；**2026-09-27 为分流公告破了唯一一次例**，见 §16）。**代价**：能答"哪个村的复购在掉"，不能答"哪款货在掉" |
| §15 分流链路 ③「分流产生的到访写入 `trip_checkin`，大屏显示分流贡献量」 | **部分实现**：`trip_checkin` 已建（`db/V10__m6_trip_chain.sql`，user_id → app_user）；M6 渠道判定已能基于足迹把订单归到 `TRIP`（3 天窗口，`OrderService.TRIP_WINDOW_DAYS`）。**未实现的两块**：① 服务端**没有把分流公告的浏览记为 `source=DIVERSION`** 的写入方 —— 客户端瞎传会被忽略（验收 B9），但系统自己也没触发；② 运营端"分流贡献量"数字面板**未做**。**答辩时只讲**：足迹 → 订单渠道归类（M6）这条线；不讲"分流公告自己回流到足迹"这一段 | `trip_checkin.source` 字段已为 `DIVERSION` 留位（验收 D3 注释写明"尚无写入方"），但 `DiversionNoticeController` 与 `TripController` 之间**没有回调** —— 这是已识别但故意未做的边界：分流公告作用对象是游客的"当下决策"，把它当作到访会让 DIVERSION 与 REAL 互相稀释 |
| §15 分流链路 ①「管理端：一键下发**推荐位**」 | 实现为「一键生成**公告草稿** → 人工改文案 → 发布」，游客端以**首页告警条 + 详情页 banner** 呈现。**没有"推荐位"这个概念**（首页轮播/精选不参与分流） | "推荐位"要改首页的运营内容，而那条链路没有审核与撤回；公告是独立一张表、独立发布动作，**出错可以撤下**。且公告**必须人工发布**：承载率来自仿真数据，让系统自动对游客喊话，出错时没人拦得住 |
| §15 分流链路 ②「游客端：AI 行程规划时 `rural_agent` 权重上调，生成乡村替代方案」 | **未实现**：公告是**独立展示**，不会改写已生成的行程；`plan_itinerary` 也没有"因承载高而调权重"这个输入 | 真要做需要把当日承载接进 M4 的排序输入，那会让**同一句话问两次得到不同行程** —— 演示时不可解释。当前做法是**把候选点摆出来、点进详情页**，决定权留在游客手里 |
| §15 规则 5「乡村**到访**高 **且** 体验→购买转化率 < 阈值」 | 去掉"到访高"这个前置条件，改成 **近 7 日体验参与 ≥ 20 人次** 的样本下限；分母也从"到访人次"改成"体验参与人次" | 两个理由都写在 `RuleEngine.evalLowConversion` 的注释里：① 分母用"到访人次"会让所有乡村点转化率被稀释到很低、规则全部误报 —— 路过村子没参加体验的人没买东西，说明不了转化问题；② 样本太小时 0% / 100% 都没有意义，"到访高"这个门槛换成样本下限才真正解决误报 |
| §16 `poi_visit_stats` 的 `hour` 列 | **未实现**，只有日粒度 | 小时级要真有小时级数据源；合成数据做小时级等于编得更假。同理"单点小时级客流"不做 |

其余部分（规则 1/2/3/4 的触发条件、判定与 LLM 分离、工单闭环、幂等重扫）**按设计稿落地，没有偏离**。

> 为什么不能靠聚合省掉：公告要记**谁在什么时候发了什么**（`published_by`/`published_at`），
> 以及**那一刻的候选快照**（`candidates_json`）。快照必须落库 —— 公告是"那一刻的决定"，
> 不是一个实时视图；不落库的话昨天发的公告今天再看会显示今天的承载，运营无法解释自己发过什么。
> 这与"能聚合就不建表"不冲突：它是**事件记录**，不是可聚合的派生数据。

> **2026-09-27 补：`poi` / `experience` / `product` 三张表各加了一列 `source`（`db/V11__m10_resource_admin.sql`）。**
> **不是新表**（表数仍是 20），是给"带 `city_code` 的表"补一条**行的来源标记**。
> 起因：`CityPackImporter` 每次启动按 `city_code` **全量删除重灌**这三张表 —— 运营在管理端新建的资源
> 会在下次重启时被清掉。加 `source`（`PACK` 数据包导入 / `ADMIN` 运营新建）后，导入器的删除条件
> 从 `city_code = ?` 收窄为 `city_code = ? AND source = 'PACK'`，运营建的行就不受影响。
> **为什么不用"另建一张运营资源表"绕开**：那会让景点在两处各存一份，游客端要 UNION、
> `poi_relation` 要认两套 id、M4 行程规划要判两次 —— 换城市时更是一起崩。

> **2026-09-28 补（M10 续）：新增第 21 张表 `poi_comment`，并给 `poi` 再加四列。**
> ① **`poi_comment`**（`db/V12__m10_poi_edit_comment.sql`）：`poi_id` 直连 `poi.id`、
> `user_id` → `app_user.id`（复用 M8，**没有为评论另建用户体系**）、`content` / `rating(1~5)` /
> `status(PENDING/APPROVED/HIDDEN)`。**不带 `city_code`** —— 评论是用户产生的，
> 不能随数据包重灌消失。游客端"来过的人怎么说"与口碑评分从此走真表
> （整个 `web/src/mock/` 目录已删除，含 `reviews.ts` / `stats.ts` / `hash.ts`）。
> ★ 与第 14 行 `feedback` 的关系：设计稿是**一张表评四种对象**（`target_type` 泛化），
> 实际建的是**只评 POI 的专用表**。理由：本轮只有"景点评论"这一个真实需求，
> 泛化表要多维护 `target_type` 的分支校验与渲染，而**没有第二个对象需要评**；
> M6 的 `order_review` 也已存在，它评的是"这次交易"而不是"这个景点"。
> ② **`poi` 加 `address` / `phone` / `detail` / `warning_threshold` 四列**：
> 前三列是**数据包态**（包里没有值，靠运营在管理端填，留空就不显示，不开天窗）；
> `warning_threshold` 是**运营态** —— 景点级预警阈值，接了 `RuleEngine` 的 OVERLOAD 预警档，
> **景点级优先、回退全局**。现有 42 条该列全为 NULL，所以**行为与之前完全一致**；
> 一级档「已超载」不受它影响（装不下就是装不下，是物理事实）。
> ③ **表数从 20 变成 21。** 这是第二次破例，理由与第 20 张不同：它不是"事件记录"，
> 而是**用户产生的内容** —— 不可能由数据包或规则聚合出来，必须有地方存。
> **代价说清楚**：`source` 是**导入器与运营端之间的约定**，任何新增的"按 `city_code` 全量重建"的代码
> 都必须带上 `source = 'PACK'`，否则这个隔离就漏了。
> 注意与既有两个同名列**语义不同**：`poi_image.source` 是 `UPLOAD`/`SEED`（配图从哪来），
> `trip_checkin.source` 是 `REAL`/`SIM`/`DIVERSION`（到访怎么来的）。

> **同一次改动还有一半：`status` 也不再被重灌覆盖。** `poi` / `experience` / `product` 的 `status`
> 列（V1/V2 就有，"1 上架 / 0 下架"）**不在数据包里** —— `citypack/*.json` 没有这个字段。
> 原先导入器硬编码 `setStatus(1)`，等于**每次重启都把运营的下架动作撤销掉**。
> 现在改成：重灌前先记下 `status != 1` 的行，插完按原状态还原。
> **为什么这一半不能省**：数据包资源**既不能删、也不能改字段**，所以"下架"是运营
> 唯一能让它从游客端消失的手段 —— 撤销它，42 条现有资源就一条也藏不住，
> "下架优先于物理删除"这条产品原则对全部现有数据直接失效。
> 一句话记法：**`source` 管"哪些行不该被清"，`status` 管"这些行的运营态不该被清"**。

**明确不建的表（避免过度设计）**
- ❌ `product_sales_stats`：销售统计用 `order_item JOIN orders` 聚合即可，不建宽表、不做双写。真慢了再加视图。
- ❌ `visitor_profile`（独立画像表）：画像放 `visitor.tags_json` + 查询时实时聚合，不单独建表。
- ❌ `merchant`（独立商户表）：商户作为 `poi` 的一类 + 关联字段，不另起炉灶。
- ❌ `sku / spec / coupon / address_book / logistics`：P3，一律不做。

## 22. 三个核心创新点

> 原方案 4 个方向里，C（统一数据模型）**降级为技术支撑**，因为它回答不了"解决了什么别人解决不了的问题"。

### 创新点一：承载力驱动的文旅客流"下乡"智能引导
**什么问题**：热门景区超载与周边乡村闲置同时发生，现有系统只预警、不调度。
**怎么做**：规则引擎识别"主景区 >80% 且周边乡村 <20%" → 分流工单 → 动态上调 `rural_agent` 权重 → **改写游客行程** → 分流到访回流进大屏"分流贡献量"。
**为什么新**：把"监测预警"推进到"调度闭环"，游客端和管理端**联动**，不是两个独立系统。
**能演示**：演示 2:10–3:10 段，行程被真实改写。

### 创新点二：以"体验锚点"为核心的文旅消费链离境延伸
**专业表述**：**从"到访消费"到"离境复购"的文旅消费链延伸机制**
**什么问题**：旅游消费一次性归零，乡村产业拿不到长期客源。
**怎么做**：产品强制挂靠体验与产地（数据库层约束）→ 体验产生足迹 → 足迹成为复购推荐的**唯一输入** → `product_agent` 输出"你体验过什么"而非"你想买什么"。
**为什么新**：推荐系统的输入是**体验记忆**不是**商品类目**，这是与电商推荐的本质区别；技术上体现为 `order_item.experience_id` 溯源 + `orders.channel` 复购标记。
**能演示**：演示 4:20–5:10 段，"两周后"回来复购。

### 创新点三：规则引擎与多智能体协同的双向决策中枢
**什么问题**：纯 LLM 做运营分析不可控、不可解释；纯规则做旅游规划不够个性。
**怎么做**：**判定用规则（确定性、可解释），生成与解释用 LLM（灵活性）**，二者不越界；同一套多智能体**同时服务游客（生成行程）和管理者（生成建议）**。
**为什么新**：明确了"确定性/概率性"的职责边界，规避幻觉；一套 Agent 双向复用。
**能演示**：点击「AI 解读」→ 三段式归因 → 一键转工单。
**已经落地的一处**（M3 问答，2026-09-26）：`topic_gaps` 规则判定**只决定**"用不用知识库、提示词有多严"（确定性），
最终答案由 DeepSeek 生成（灵活性）。两者不越界 —— 规则不再直接决定"答不答"，
模型也不被允许编造本地事实。三条链路（`rag` / `constrained` / `general`）与
`generator` 字段（记录这条回答**实际**由谁产出：模型名 / 缓存 / 摘录）都能在答辩现场实时演示。

**一句话串起来**：
> "我们让 AI 既把游客送进乡村，也让乡村在游客回家之后还能继续赚钱——并且这套判断有规则兜底，不是靠大模型拍脑袋。"

## 23. 技术风险与兜底

| # | 风险 | 概率 | 兜底方案 |
|---|---|---|---|
| 1 | **LangGraph 多 Agent 调不通** | 高 | 先做单 Agent 版本跑通 → 再上图；节点降到 3 个（parse→synthesize→critique），Agent 变普通并发函数。**"多智能体"的故事靠 6 个 Agent 类支撑，不靠图的复杂度** |
| 2 | **现场断网 / LLM 限流 / 响应慢** | 中高 | 预生成问答入缓存（**已落地：16 组 / 76 条可命中问法**）+ 5 套行程 + 复购推荐结果；`DEMO_MODE=true`；3 分钟录屏。**离线不是只靠缓存**：命中缓存走回放，未命中但问题在知识库范围内走**原文摘录**（仍有出处），只有"本来要靠模型才能答"的问题才会明确说明离线边界 —— 断网时链路不会白屏，也不会假装答上了 |

## 24. 商业化与实际应用扩展

**短期（比赛后 3 个月）**
- City Pack 复制到陕西其他地市（安康、商洛），验证迁移成本 < 1 人日
- 对接真实数据源适配器：`DataSourceAdapter` 接口预留，可接票务系统、手机信令客流、互联网投诉

**中期（落地路径）**
- **私有化部署**：LLM Provider 抽象层支持切 Ollama + Qwen，县域政府普遍不接受文旅数据出网——这是**真实的付费理由**，写进商业计划书
- **形态轻量化**：微信小程序端（游客真正会用的形态），管理端保留 Web
- **乡村合作社接入**：为经营主体提供简易上传入口（P3 阶段再做，比赛不做）

**长期价值**
- 从"门票经济"→"体验经济 + 产品经济"的可量化路径：**复购率**是你给县域政府最直观的 KPI
- 沉淀的"体验—产品—复购"数据，可反哺乡村选品与产能规划
