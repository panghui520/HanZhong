## 一、问题：为什么"说不明白"

用户问「帮我规划一个汉中两日游」，系统原本走 `knowledge_search`，命中数据包里的
《汉中行程怎么组合》—— 那是一篇**散文**，讲的是排行程的**原则**
（"先按方向分组""一天累计超过 360 分钟基本装不下"），

给不出"你的两天具体去哪几个点"。

**排行程的算法不该只存在于文档里。** 用户的评价"说不明白"是准确的：他问的是
一份**具体方案**，系统给的是一段**方法论**。

## 二、设计

### 2.1 把知识库里的原则变成代码

| 知识库《汉中行程怎么组合》里的原则 | `itinerary.py` 里的实现 |
|---|---|
| 先按方向分组，方向相反的不要排同一天 | **同一天只排一个区县** |
| 中心是汉台区 | 城市中心所在区县**排在第一天** |
| 一天累计超过 360 分钟基本装不下 | `MINUTES_PER_DAY = 360` 作为每日预算 |
| 用"建议游览时长"做预算 | 每个 POI 的 `duration_min` 累加，装不下就换一天 |

这些不是新造的规则，是**已经写进给用户看的文档**里的经验值。代码与文档同源，
所以解释"为什么这么排"时能直接引到出处（`citypack/hanzhong/docs/08-districts.md`、
`20-scenic-guide.md`、`26-itinerary.md`）。

### 2.2 选点与顺序**必须分开**（第一版就栽在这里）

第一版把"级别优先"和"最近邻"混成一个排序：先按级别排、再在整表上做最近邻。
结果是**最近邻把级别完全覆盖**了 —— 汉台区排出的是「古汉台 + 拜将坛 + 天汉湿地」
（三个 3A，因为它们都在市中心、离中心点最近），而石门栈道、兴汉胜境两个 4A
因为离得远被挤到预算之外。

拆成两个函数：

- `_rank_by_level()` —— **只决定"选哪些点"**：级别高的在前，同级按时长降序。
  偏好（"亲子"这类）命中 `tags` 的点排到最前，但**不改变级别权重**。
- `_nearest_order()` —— **只决定"怎么走"**：**只在当天已选的点之间**做最近邻。

> **"顺路"只在同一天已选的点之间才有意义。** 在整张表上做最近邻，
> 等于让"离市中心近"压过"值不值得去"。

### 2.3 只用景点与乡村点

`business_type` 有 5 类（`SCENIC` 18 / `RURAL_SPOT` 12 / `FOOD` 6 / `LODGING` 4 /
`TRANSPORT` 2），行程的游览点**只取前两类**（共 30 个）。餐饮与住宿是配套
（用户自己决定，助手另有工具帮他找），交通枢纽是出入口不是景点 ——
把"汉中站"排进"第一天的景点"是明显的错误。

### 2.4 起点区县：用户住哪就从哪开始

用户在卡片上选过酒店后，行程应该**从他住的区县开始排**，第二天不该让他先跨一个县
再回来。上下文里的住处只有坐标（`location`），没有区县字段。

这里**刻意不加那个字段**，而是用 `ItineraryPlanner.district_of("lng,lat")`
现算：加字段的话它要么是导入时算的、要么是前端传的，两条路都可能与坐标不一致；
从坐标现算只有一处真相。

### 2.5 与 `knowledge_search` 的分工（这是最容易混的两条路）

| 用户问的 | 走哪条 | 因为 |
|---|---|---|
| 「帮我排一个汉中两日游」「三天怎么玩」 | `plan_itinerary` | 要的是**具体方案**：哪天去哪几个点 |
| 「行程一般怎么安排比较好」「一天排几个景点合适」 | `knowledge_search` | 要的是**原则**：那篇文档讲的是排法本身 |

混起来的后果是：问"怎么排"时系统硬给一份两日游（用户还没说几天），
问"两日游"时系统讲一堆原则却不给点。所以两条路都留着，由调度器按
"有没有点名天数 / 要方案还是要方法"来分。**实网验证第 4 例就是这一条**
（见第四节），它**没有**走行程工具。

### 2.6 这一层不做的事（都是刻意的）

- **不算车程**：数据包里的经纬度是**基于规则的估算值**（`meta.json` 的
  `disclaimer` 已声明），据此算出的"车程"是假精度。所以只给"同一天在同一区县"
  这个**结构性保证**，具体怎么走交给地图导航。
- **不排餐饮与住宿**：不替用户决定在哪吃、住哪。
- **不做门票与开放时间的实时校验**：数据包里是静态整理值，输出时**如实标注来源**，
  不假装是实时信息。
- **不落库**：行程是**算出来的**，不存 `trip_plan` 表 —— 它完全由数据包决定，
  存下来只会在数据包更新后变成一份过期副本。

## 四、验收结果

### 4.1 离线自检（`scripts/eval_agent.py`）

```
【1】工具规格      工具 4 个：search_nearby、search_poi、knowledge_search、plan_itinerary
【2】工具清单渲染   amap 开：4 工具 + 类型码；amap 关：知识库 + 行程规划 + 原因说明
【15】行程规划      30 个游览点；两日游=['汉台区', '南郑区']；三日游=['汉台区', '南郑区', '留坝县']
                   每天只排一个区县、点不重复、不超预算；起点随住处；天数有兜底与上限；
                   数据包缺失时报错而非空行程

通过：226 项断言全部成立
```

【15】段覆盖的**边界**（都是"不抛异常、只会安静排错"的那类）：

- 同一天串了两个区县 / 某天的区县标签与该天景点不一致
- 同一个游览点在行程里出现两次（两日 / 七日都测）
- 单点就超出每日预算 / 一天被标成 `over_budget`
- 三日游的区县应各不相同（第一轮每个区县各占一天）
- 天数兜底（没给 / 非数字 / 0 → 2 天）与上限（99 → 7 天）
- `district_of` 对非法坐标返回空串而不是抛异常
- 数据包不存在 → `planner.ready` 为 False、`plan()` 返回空行程
- `planner=None` / 数据包为空 → **`error` 而不是空结果**（"本机没数据"≠"查了没有"）
- 住处坐标驱动起点；住处坐标坏掉时**不崩**
- `_price_text`：0 → 免费、null → 不说（**不能把未知说成 0 元**）
- 调度器提示词里有这个工具、且区分了"方案 vs 原则"；`{city}` 等占位符已替换
- 呈现约束四句都在（原样呈现 / 以景区公告为准 / 不编造交通方式 / 不含餐饮住宿）
- `_parse_decision` 认得 `plan_itinerary`

## 五、顺手修的两处（都在同一批改动里，理由如下）

### 5.1 高德未配时，`meta.tools` 报的是假话

`agent.stream()` 里原来写的是"高德没配就只报 `knowledge_search`"。加了
`plan_itinerary`（**不需要高德**）之后这句话就变成假的了 —— 前端会据此把
行程示例藏起来，而它其实可用。改为与 `/ai/health` 共用 `tools.available_tools()`。

同理，`tool_menu` 在高德未配时补了一句"`knowledge_search` 与 `plan_itinerary`
**不受影响**" —— 否则清单里列着行程工具、上面却说"问真实地点一律选 `none`"，
模型会把"排两天行程"也当成问真实地点而弃用。

### 5.2 助手页的回答不渲染 `**加粗**`（M4 阶段一遗留）

知识问答页（M3）有一个 `renderText()`：先转义 HTML，再把 `**加粗**` 换成
`<strong>`。助手页（M4）当时漏了，回答里是一串字面的星号。

抽成 `utils/format.ts` 的 `inlineText()`，两页共用（**M3 行为完全不变**，
它原来调的就是同一份实现）。同时在 `SYSTEM_PROMPT_TOOLS` 规则 5 里
**明确禁止 Markdown 标题**（`#` / `##`）—— 回答是按纯文本段落渲染的，
写成 Markdown 标题会原样显示成一串井号。实网验证第 1 例改前就出现了
`# 汉中两日游行程` / `## 第 1 天 · 汉台区`，改后 `answerHasHashHeading=false`。

> 为什么不引一个 Markdown 库：那会连带处理链接、图片、内联 HTML，而回答里的
> 链接必须来自知识库元数据（见 `_source_payload`），交给模型写就有编造的可能。

## 六、已知边界（答辩要能说清）

1. **行程是"排哪几个点"，不是"怎么走"。** 没有车程、没有路线、没有交通方式 ——
   数据包的坐标是估算值，据此算车程是假精度。用户问"怎么过去"时，助手会说明
   需要自行用地图导航查询（提示词规则 12 已约束）。
2. **天数上限 7 天**，且**数据不够时不硬凑**：可排的点不够时如实说明
   "只够 N 天"，不重复推荐同一个点。界面上有一条黄色提示显示这件事。
3. **同一区县的可排天数由 `MINUTES_PER_DAY` 决定**：一个区县总时长超过 360 分钟
   时会拆成两天（`rounds` 循环回头加天），但**两日游不会给同一个区县两天** ——
   第一轮每个区县各占一天，这样两日游是"中心一天 + 最值得去的周边一天"，
   而不是"中心两天、别处一天没有"。
4. **偏好是软约束**：命中 `tags` 的点排到最前，但不保证整份行程都是偏好类型
   （某个区县可能一个偏好点都没有）。
5. **不落库、不缓存**：每次提问现算。所以数据包一改，下一次提问就是新结果 ——
   这是有意的，存下来只会在数据包更新后变成过期副本。
