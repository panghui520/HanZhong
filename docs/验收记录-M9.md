# M9 媒体与配图管理 · 验收记录

> 验收日期：2026-09-25 · 结论：**通过（后端 + 前端）**
> 模块范围：`db/V4__m9_media.sql` → 后端上传/替换/删除/排序接口 → 前端图片位接入 + 管理端「图片管理」页
> 需求来源：用户明确要求「管理轮播图 + 分别管理每个景点的图片，支持上传、替换、删除和排序」；
> 并明确**跳过 AI 生成图片**（真实照片由用户自行提供）。

## 一、模块职责边界

**做**：首页轮播帧（文案 + 图片 + 启停 + 顺序）的增删改查；
每个景点独立的多张配图（上传 / 替换 / 删除 / 排序 / 设封面）；
把配图接进游客端所有图片位；管理端一个「图片管理」页承载全部操作。

**不做**：图片裁剪与压缩、多尺寸缩略图、CDN、水印、图片审核、批量导入。
这些都不在需求里——需求要的是"运营能自己换图"，不是"一个图片处理平台"。

**为什么 M9 独立编号而不并入 M1**：和 M8 同源的理由。配图是**横切关注点**——
M1 的景点、M2 的产地、M4 的行程停留点都要显示图片，但它不属于任何一个。
塞进 M1 会让 M1 的职责变成"资源 + 媒体存储"两件事。

**一条不可违反的边界**：媒体表**不带 `city_code`**。
`CityPackImporter` 每次启动按 `city_code` 全量删除并重灌业务表；
`poi_image` 与 `site_banner` 只要不挂 `city_code`，就永远不会被导入器碰。
这不是巧合，是设计——**运营上传的图片是运行期数据，不能因为重启服务就消失**。
本轮已实测验证（见「四、关键设计验证」第 1 条）。

**三条设计红线没有被触碰**：M9 不新增任何电商入口（配图只挂在已有 POI 上），
不引入新的 AI 能力，也不改变 M1–M3 的任何接口行为。

## 三、接口定义

### 游客端（公开，未登录可访问）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/media/banners` | 轮播帧，**只返回启用中的** |
| GET | `/api/media/poi-images` | 配图列表。带 `?poi_id=` 只看某个景点 |
| GET | `/api/media/poi-images/covers` | `poi_id → url` 映射。列表页一次取回，避免逐张发请求 |
| GET | `/api/media/**`（文件） | 上传的图片本体，由静态资源映射直出，不经 Controller |

### 运营端（`/api/admin/**`，`hasRole("OPERATOR")`）

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/media/poi-images` | 配图列表（含全部，带 `?poi_id=` 过滤） |
| POST | `/api/admin/media/poi-images` | 上传（multipart：`poi_id` / `file` / `alt_text`） |
| PUT | `/api/admin/media/poi-images/{id}/image` | **替换文件**，保留排序与封面身份 |
| PATCH | `/api/admin/media/poi-images/{id}` | 改备注 / 设封面（`alt_text` / `is_cover`） |
| DELETE | `/api/admin/media/poi-images/{id}` | 删除（库 + 磁盘） |
| PUT | `/api/admin/media/poi-images/order?poi_id=` | 重排。体为 `[id, ...]` 完整顺序 |
| GET | `/api/admin/media/banners` | 轮播列表（**含已停用的帧**） |
| POST | `/api/admin/media/banners` | 新建帧（multipart，图片可选） |
| PATCH | `/api/admin/media/banners/{id}` | 改文案 / 启停（**刻意不动图片**） |
| PUT | `/api/admin/media/banners/{id}/image` | 替换图片 |
| DELETE | `/api/admin/media/banners/{id}/image` | 清除图片（回落到插画，文案保留） |
| DELETE | `/api/admin/media/banners/{id}` | 删除整帧 |
| PUT | `/api/admin/media/banners/order` | 重排。体为 `[id, ...]` 完整顺序 |

**错误码（5xxx 段）**：`5001` 未选择图片 / `5002` 格式不支持 / `5003` 图片过大 /
`5004` 保存失败 / `5005` 配图不存在 / `5006` 轮播帧不存在 / `5007` 排序参数不合法。

**读写分成两条前缀**（`/api/media/**` 只读、`/api/admin/media/**` 写），
而不是在同一条路径上靠 HTTP 方法区分——这样 `SecurityConfig` 的规则能一句话写清：
**公开的只有 `GET /api/media/**`**，其余落到兜底的"需要登录"。

## 四、关键设计验证

### 1. 媒体表不被 CityPack 重灌清空（实测）

`CityPackImporter` 是 `ApplicationRunner`，每次启动全量删除并重灌业务表。
实测流程（`.workbuddy-ai/tmp/media-persist.sh`）：

```
before：上传 2 张景点配图 + 新建 1 帧轮播（共 5 帧）→ 4 通过 / 0 失败
（重启后端）
after ：景点配图记录仍在（2 张）· 封面记录仍在 · 封面映射仍指向同一张图
        图片文件仍可访问 · 轮播帧仍在（5 帧）· 轮播帧 id 未变
        M1 业务表已重灌（42 处资源）        ← 确认重启真的生效了
        → 11 通过 / 0 失败
```

最后一条是关键：它证明**这次启动确实重灌了 M1 的业务表**，
所以"配图还在"不是因为重启没成功，而是因为导入器确实没碰这两张表。

### 2. 上传的图片确实能被游客读到（实测）

上传后立刻用返回的 `url` 直接请求：HTTP 200、`Content-Type: image/png`。
同时验证了静态资源映射**挡住了 `../` 目录穿越**（请求 `/api/media/../application.yml` 拿不到文件内容）。

### 3. 删除与替换的顺序（代码约束）

**先动数据库，再动文件。** 反过来的话，文件已删而事务回滚，库里会留下一行指向不存在文件的记录——
表现为页面上一个破图，且很难查。按现在的顺序，最坏情况只是磁盘上多一个没人引用的孤儿文件，无害。
实测：替换后旧文件已从磁盘清除；删除后文件已从磁盘清除。

### 4. 封面不变量（实测）

**同一 `poi_id` 下至多一张 `is_cover = 1`。** MySQL 的部分唯一索引写法不通用，
所以这个不变量由 `MediaService` 单点维护。实测三条路径：

- 给原本没图的景点传第一张 → 自动成为封面（否则运营传完图回列表页发现卡片还是插画，很反直觉）
- 把第二张设为封面 → 第一张自动归 0，封面标记仍然只有 1 个
- 删掉封面 → 剩下的第一张自动升为封面（否则列表页会突然从实拍图退回插画）

### 5. 排序语义（实测）

**传"期望的完整顺序"（id 列表），不是若干次两两交换。** 前端把当前列表顺序整理好发来即可。
后端校验这批 id **恰好等于该景点的全部图片，不多不少**——只做部分重排会把没提到的图排到不确定的位置上。
实测拒绝：只传一部分、传别的景点的 id、传空数组，三种情况均返回 `5007`。

### 6. 上传校验的三层（实测）

| 场景 | 期望 | 实测 |
|---|---|---|
| `text/plain` 文件 | `5002` | ✅ |
| 不带文件 | `5001` | ✅ |
| 不存在的景点 id | `1001` | ✅ |
| `poi_id=../../evil` | 被拒 | ✅ `1001`（在 `requirePoi` 就挡住，走不到文件系统） |
| 4.1 MB（< 5 MB 业务上限） | 放行 | ✅ `0` |
| 5.5 MB（> 业务上限，< 容器上限） | `5003` | ✅ |
| 7.2 MB（> 容器上限） | `5003` | ✅（由 `MaxUploadSizeExceededException` 处理器转换，而不是 9000） |

### 7. 无图兜底（实测，16 条断言全通过）

这是"离线可演示"这条硬约束的直接验证。把库里的图片全部清空后重测：

```
首页     Hero 仍是 4 帧、全部回落手写 SVG、15 个图片位无空块、无破图
探索页   21/21 图片位是插画、无空块、无破图、文本量未缩水（2766 字）
详情页   Hero 回落插画、不显示实景照片条、无破图
行程页   6/6 停留点图位回落插画
```

**前端不用空 `src`**：空 `src` 会让浏览器去请求当前页面地址，表现为一次莫名其妙的重复加载。
`PoiImage.vue` 在没有地址时**根本不渲染 `<img>`**，直接渲染 `SceneArt`。

### 8. 重启后的 URL 契约

`BannerVO.url` 在 `image_path` 为空时为 `null`。后端全局配了
`default-property-inclusion: non_null`，所以**这个字段会被整个省略**，
前端拿到的是 `undefined` 而不是 `null`。

因此前端判断"有没有图"必须写 `if (x.url)`，**不能写 `x.url !== null`**（后者恒成立）。
这条已写进 `types/index.ts` 的注释里——它是那种"看代码看不出来、运行时才炸"的契约。

## 六、踩过的坑（写下来避免重复）

### 1. `spring.servlet.multipart` 不是 `server.servlet.multipart`

`application.yml` 里 `server.servlet` 下已经有 `encoding` 配置，
我顺手把 `multipart` 也写在了那里——**这个位置 Spring Boot 根本不认**，
于是容器继续用默认的 **1MB** 单文件上限，4.1MB 的测试图在进入 Controller 之前就被拒了。

正确位置是 `spring.servlet.multipart`。同时上限要**略大于业务上限**（容器 6MB / 业务 5MB）：
5–6MB 的文件能被业务校验拦下并返回有指导意义的 `5003`；
若容器上限也设成 5MB，超限请求会先被容器拒掉，前端只能收到一个没有业务含义的报错。

这个坑反而实证了 `MaxUploadSizeExceededException` 处理器是有效的——
它把容器抛出的异常转成了 `5003`，而不是让前端拿到 `9000`「服务内部错误」。

### 2. 沙箱里 `Edit` 工具会"报成功但没落盘"

本模块遇到**两次**：`SecurityConfig` 的 `/api/media/**` 白名单、`application.yml` 的 `multipart`。
两次都表现为"编译通过、启动正常，但接口返回 4001 / 上传仍受 1MB 限制"。
**每次改完必须用 `grep` 复核**，否则会带着"已改"的错觉往下走。
（M2 也遇到过两次，这是第 3、4 次。）

### 3. 验收脚本里的两个假通过

- **`#len` 取错了对象**：`jq_ '#len'` 量到的是整个 `Result` 对象（`code`/`message`/`data` 三个键），
  不是 `data` 数组的长度。所有"张数 == N"的断言都拿 `3` 去比，看起来像接口坏了，其实是脚本坏了。
  改成 `data.#len`。
- **对 `<input>` 读 `innerText` 恒为空**：`readTexts` 用 `innerText` 读输入框的 `value`，
  结果两边都是 `""`，`"" === ""` 成立 → **排序断言在什么都没验的情况下通过了**。
  表单控件必须读 `.value`。这类"假通过"比"假失败"危险得多。

### 4. 键不存在 ≠ 脚本出错

后端配了 `non_null`，值为 null 的字段会被整个省略。脚本里"取不到"正是"该字段为空"的表达方式，
一开始把它当成 `ERR` 报错，误判了 3 条断言。

### 5. `result` 里不能用 `<input>` 的 `value` 属性做默认值

（本模块未踩，但同源）`v-model` 已经双向绑定，再用 `:value` 会冲突。管理端所有输入框只用 `v-model`。

## 七、已知限制与后续扩展点

| 限制 | 现状 | 扩展方式 |
|---|---|---|
| 没有图片压缩 / 缩略图 | 原图直出，单张上限 5MB | 上传时生成缩略图列，`PoiImageVO` 加 `thumb_url` |
| 排序只有上移/下移 | 不做拖拽，避免引入拖拽库 | 前端换拖拽库，后端接口不用改（语义已是"完整顺序"） |
| 没有批量操作 | 一次一张 | 上传接口改成接收 `MultipartFile[]` |
| 没有权限细分 | 所有 OPERATOR 都能改全部图 | 加 `poi_image.owner_id`，或按区县分权 |
| 图片不入版本库 | `media/` 在 `.gitignore` 里 | 演示前需把媒体目录一并拷到演示机（见下） |

**⚠️ 演示前必须做的一件事**：`media/` 被 `.gitignore` 忽略，
所以运营在开发机上传的图片**不会跟着 `git clone` 走**。
换机器演示前，要么把整个 `media/` 目录拷过去，要么在演示机上重新上传。
这一点也写进了 `.gitignore` 的注释里。
