## 一、模块职责边界

**做**：
- 在**既有**管理端（`AdminLayout.vue` + `/admin/**` 路由）里加一页，**不新建后台**；
- 景点 / 美食 / 农产品三类资源的**列表、搜索、状态筛选、新增、编辑、上架、下架、删除**；
- 让"运营新建的资源"**不被 `CityPackImporter` 的启动全量重建清掉**；
- 让"运营设过的上下架状态"**同样活过重启**（第二轮补，见「四」的 4.2）；
- 删除前的**引用检查**（订单 / 足迹 / 体验 / 产地 / 配图 / 关系）；
- 配图抽屉**复用 M9** 的 `poi_image` 能力（上传 / 设封面 / 排序 / 删除）。

**不做**（每一条都有理由）：
- **不新建资源表** —— `poi` / `experience` / `product` 已由 M1/M2 建好，重造一张等于把景点存两份；
- **不做体验项目（`experience`）与商户的 CRUD** —— 见「九、文档回核」第 1 条（★ 答辩时不能讲"有商户管理"）；
- **不让运营改数据包带来的行的字段** —— `source='PACK'` 的行**编辑与删除**都拒绝（报 `1108`），
  理由见「四」；**但上下架不锁**（`status` 是运营态、不会被重灌覆盖，见 4.2）；
- **不做物理删除的"级联清理"** —— 被引用即拒绝，不替运营决定"删资源时顺手删掉订单溯源"；
- **不改 M1–M9 已验收接口的契约** —— 新增的 11 个端点全在 `/api/admin/resources/**` 下。
  （第二轮改了 `PoiServiceImpl` / `ProductServiceImpl` 的**实现**，但只是补上 `listXxx` 本来就有的
  status 过滤，**端点路径、请求、响应结构一个都没动**。）

**两条红线没有被触碰**：
1. **不是电商** —— 农产品挂 `poi_id` / `experience_id`（沿用 V2 的 `chk_product_traceable`），
   管理端只维护这条链上的字段，**没有独立的商城/店铺概念**；
2. **不是"另起一套后台"** —— 路由挂 `/admin/resources`（继承 `meta.requiresAdmin`）、
   菜单插进 `AdminLayout.menus`、样式沿用该页 scoped 的 `.panel`/`.field`/`.modal` 体系，
   `AdminLayout.vue` 的改动**只有 4 行**（一句注释 + 一个菜单项），没动样式。

## 三、接口定义

全部挂在 `/api/admin/resources` 下 → 自动继承 `SecurityConfig.ADMIN_PREFIX` 的 `hasRole("OPERATOR")`。
**`SecurityConfig` 一行都没改** —— 这正是 M8 预留 `ADMIN_PREFIX` 的意义。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/admin/resources/pois` | `?type=scenic\|food`、`?keyword=`、`?status=0\|1`。`type` 决定业态白名单（`scenic` → `SCENIC`+`RURAL_SPOT`；`food` → `FOOD`） |
| POST | `/api/admin/resources/pois` | 新增。编码自动生成 `P-ADM-###`，`source=ADMIN` |
| PATCH | `/api/admin/resources/pois/{id}` | 编辑。**`source='PACK'` 直接报 1108** |
| PATCH | `/api/admin/resources/pois/{id}/status` | 上下架。`body.status` 只接受 `0`/`1` |
| DELETE | `/api/admin/resources/pois/{id}` | 删除。被引用报 1104；PACK 行报 1108 |
| GET | `/api/admin/resources/products` | `?keyword=`、`?status=` |
| POST | `/api/admin/resources/products` | 新增。编码 `PRD-ADM-###` |
| PATCH | `/api/admin/resources/products/{id}` | 编辑 |
| PATCH | `/api/admin/resources/products/{id}/status` | 上下架 |
| DELETE | `/api/admin/resources/products/{id}` | 删除。`cart_item.product_id` / `order_item.product_id` 有引用即报 1104 |

**错误码（`ErrorCode` 1xxx 段续号）**：

| 码 | 常量 | 文案 |
|---|---|---|
| 1101 | `RESOURCE_NOT_FOUND` | 资源不存在或已被删除 |
| 1102 | `RESOURCE_TYPE_INVALID` | 资源类型不合法 |
| 1103 | `RESOURCE_NAME_REQUIRED` | 请填写资源名称 |
| 1104 | `RESOURCE_IN_USE` | 该资源已被订单、行程或足迹引用，不能删除，请改用下架 |
| 1105 | `RESOURCE_CODE_DUPLICATE` | 资源编码已存在，请换一个 |
| 1106 | `RESOURCE_STATUS_INVALID` | 上架状态只支持 0 或 1 |
| 1107 | `RESOURCE_FIELD_INVALID` | 资源字段不合法，请检查后重试 |
| 1108 | `RESOURCE_PACK_LOCKED` | 该资源来自城市数据包，不能删除，请改用下架 |

**两处刻意偏离"标准 CRUD"**：
- **状态参数用 `String` 接再手工容错**（`parseStatus`）。用 `Integer` 接的话，前端 `?status=`（空串）
  会在 Spring 的类型转换阶段抛异常、被兜成 `9000 服务内部错误` —— 一个"筛全部"的正常操作
  会变成一条吓人的报错。空串按"不筛选"处理，非数字才报 1106。
- **`nextAdminId` 取"现有最大序号 + 1"而不是"行数 + 1"**。后者在删过一条之后会撞主键。

## 四、数据层：`source` 列与导入器隔离（本模块的技术核心）

**问题**：`CityPackImporter` 每次启动按 `city_code` **全量删除重灌** `poi`/`experience`/`product`。
运营在管理端新建的资源，下次重启就没了 —— 这不是"偶发丢数据"，是**每次启动必然发生**。

**解法**（`db/V11__m10_resource_admin.sql` + `CityPackImporter` 5 处改动）：

```java
// 原：productMapper.delete(new LambdaQueryWrapper<Product>().eq(Product::getCityCode, cityCode));
// 现：
productMapper.delete(new LambdaQueryWrapper<Product>()
        .eq(Product::getCityCode, cityCode)
        .eq(Product::getSource, SOURCE_PACK));   // ← 只清数据包带来的行
```

**为什么不用"另建一张运营资源表"绕开**：景点会在两处各存一份，游客端要 UNION、
`poi_relation` 要认两套 id、M4 行程规划要判两次 —— 换城市时更是一起崩。

**代价（写进文档，不只写在这里）**：`source` 是**导入器与运营端之间的约定**。
任何新增的"按 `city_code` 全量重建"的代码都必须带上 `source = 'PACK'`，否则隔离就漏了。

**同名列语义不同，别混**（V11 文件头写死）：

| 列 | 取值 | 含义 |
|---|---|---|
| `poi_image.source` | `UPLOAD` / `SEED` | 配图从哪来 |
| `trip_checkin.source` | `REAL` / `SIM` / `DIVERSION` | 到访怎么来的 |
| **`poi` / `experience` / `product` . `source`** | **`PACK` / `ADMIN`** | **这一行是数据包导入的，还是运营新建的** |

**迁移验收**：
- 三列均建为 `varchar(16) DEFAULT 'PACK'`；回填后 `poi=42 / experience=14 / product=16` 全为 `PACK`（与 V1/V2 注释的期望条数一致）；
- **重跑幂等**：第二次执行无报错、无重复列；
- **导入器回归**：收窄后启动日志 `[CityPack] 导入完成 city=hanzhong 资源点=42 关系=275 分类=10 体验=14 产品=16 客流统计=2520` —— 与收窄前**逐项一致**（说明隔离没有误伤数据包）。

### 4.2 `status` 是**运营态**，导入器不再覆盖它（第二轮补）

`source` 只解决了"运营新建的行别被清掉"，还漏了一半：**数据包自己的行也要能被运营下架**。

`CityPackImporter` 原先硬编码 `p.setStatus(1)`（`pois` / `experiences` / `products` 各一处）。
而 `status` **不在数据包里** —— `citypack/hanzhong/pois.json` 没有这个字段。所以"重灌时一律置 1"
等于**每次重启都把运营的下架动作撤销掉**。后果不是"少个功能"：PACK 行既不能删、也不能改字段
（`requireAdminOwned`），**下架是运营唯一能让它从游客端消失的手段** —— 撤销它，42 条现有资源
就一条也藏不住，"下架优先于物理删除"这条产品原则对全部现有数据直接失效。

改法（`CityPackImporter`）：

```java
// 删除之前先记下"被运营下架过"的行（status != 1）
Map<String, Integer> offlinePois = offlinePoiStatuses(cityCode);   // 同理 experience / product
// ...全量删除 + 重灌...
// 插完把状态写回去
offlinePois.forEach((id, status) -> { Poi patch = new Poi(); patch.setId(id); patch.setStatus(status); poiMapper.updateById(patch); });
```

- **只挑 `status != 1`**：上架是默认值，绝大多数行都是 1，读出来再逐条 UPDATE 是白做。
  多出的写操作量与"运营实际下架过的条数"同阶。
- **不做成"插入时写对状态"**：那要给三个 `readXxx` 各加一个 map 参数，而它们现在是纯函数
  （只读 JSON、不碰库）。整个 `run()` 在一个事务里，中间不会有人看见这些行短暂回到"上架"。
- **配套**：`updatePoiStatus` / `updateProductStatus` **刻意不做** `requireAdminOwned` ——
  上下架不受"改了会被重灌覆盖"那条约束，因为它本来就**不会**被覆盖了。
  编辑与删除仍然锁定 PACK 行（那两项确实会被重灌覆盖）。

**结论**：`source` 管"**哪些行**不该被清"，`status` 管"**这些行的运营态**不该被清"。两者是同一件事的两半。

## 七、删除保护（"下架优先于物理删除"）

**两道闸，都在服务端**（前端只是把按钮置灰，不是边界）：

1. **引用检查**（`poiReferences` / `productReferences`）—— 命中任一项即报 `1104`，
   且**文案点名是哪种引用**（"资源关系 / 配图 / 乡村体验 / 农产品产地 / 到访足迹 / 历史订单"），
   运营知道该先动哪里：

| 资源 | 检查的引用 |
|---|---|
| `poi` | `poi_relation`（双向）、`poi_image`、`experience.poi_id`、`product.poi_id`、`trip_checkin.poi_id`、`order_item.poi_id` |
| `product` | `cart_item.product_id`、`order_item.product_id` |

2. **数据包行锁定**（`requireAdminOwned`）—— `source='PACK'` 的行**编辑与删除都拒绝**（`1108`）。
   理由：改了下一次启动会被数据包覆盖，"过两天又变回去"比直接拒绝更糟。
   **★ 但上下架刻意不锁** —— `status` 不在数据包里、是运营态，且导入器已改成保留它
   （见「四」的 4.2），所以下架**不会**被重灌覆盖。锁掉它等于让 42 条现有资源既不能删
   也不能藏，与"下架优先于物理删除"直接冲突。`1108` 的文案"如只想让游客看不到，请改用下架"
   在编辑/删除这两条路径上是**真的可用**的出路（第二轮之前它自相矛盾：它让运营去按那个
   刚被它自己拒掉的按钮）。

**为什么"下架优先"是产品要求而不是偷懒**：物理删掉一条被历史订单引用的资源，
订单详情里的产地溯源会变成**悬空 id** —— 而那是已经发生的事实，不该被后来的运营操作改写。

## 八、踩坑与修复（两个真 bug，都值得记）

### 8.1 `hanyou_add_column` 的 `definition` **必须自带列名**

- **现象**：V11 第一次执行报 `ERROR 1064 ... near 'VARCHAR(16) NOT NULL DEFAULT 'PACK' COMMENT ...'`。
- **排查**：先查 `@@sql_mode`（不含 `ANSI_QUOTES`，排除双引号问题）→ 写 `probe_v11.sql` 打印过程里拼出的 DDL，
  得到 `ALTER TABLE \`poi\` ADD COLUMN VARCHAR(16) ...` —— **缺列名**。
- **根因**：过程内的 `CONCAT('ALTER TABLE ... ADD COLUMN ', p_definition)` **只拼列名以外的部分**；
  `p_column` 参数**只用于 `information_schema` 判重**，不进 DDL。
- **修法**：`definition` 自带列名 + 用**单引号双写**转义（对齐 V6 既有写法）：
  ```sql
  CALL hanyou_add_column('poi', 'source',
    'source VARCHAR(16) NOT NULL DEFAULT ''PACK'' COMMENT ''PACK 数据包导入 / ADMIN 运营新建；导入器只重建 PACK 行''');
  ```
- **已在 V11 文件头写死这两个坑**，避免下一个人重踩。
- 旁支：`probe_v11.sql` 自己第一版也报 1064，因为用保留字 `generated` 当别名 → 改 `ddl_text`。

### 8.2 ★ `Map.of().get(null)` 抛 NPE（`Map.of()` 与 `HashMap` 行为不同）

- **现象**：`POST /admin/resources/products` 返回 `code=9000 服务内部错误`，8 条断言失败。
- **定位**：日志 `java.lang.NullPointerException at java.util.ImmutableCollections$MapN.get(...)
  at AdminResourceServiceImpl.toProductVOs(:617) at createProduct(:243)`。
- **根因**：`NameResolver` 在 ids 为空时返回 **`Map.of()`**（不可变空 Map），
  而 **`Map.of().get(null)` 抛 NPE**（`HashMap.get(null)` 返回 null，不抛）。
  农产品**只挂体验锚点、不挂产地**时 `poi_id` 就是 null（V2 的 `chk_product_traceable` 允许），
  夹具恰好走了这条分支。
- **修法（两层，缺一不可）**：
  1. **契约层** `NameResolver`：`Map.of()` → `Collections.emptyMap()`，并写清"实测踩过"；
  2. **调用层** `AdminResourceServiceImpl`：新增 `lookup(names, id)`，`id == null` 直接返回 null ——
     调用方不再押上游的实现细节。
- **复测**：37/37 全通过。
- **同类隐患（已识别，未修，见「十」）**：游客端 `ProductServiceImpl.toVOs` 是同一个写法。

### 8.3 环境类

- 重启前必须先确认 8080 没被旧后端占着 —— 旧代码会让新端点返回 `1001 接口不存在`，
  而 health 是透传所以看着正常；
- 探针脚本用 `.workbuddy-ai/tmp/cdp.sh`（全新 profile + 随机端口）；
  浏览器验收脚本里 `window.confirm` 会阻塞渲染进程，必须监听 `Page.javascriptDialogOpening`
  并显式接受，否则后续点击全部无效。

### 8.4 ★ 两处既有缺口是**怎么被发现的**（方法比结论更值得留）

第一轮验收 37/37 + 58/58 全绿（第二轮加了 PACK 下架那段后是 72/72），但**两处缺口一次都没被碰到** —— 因为探针只在自己造的数据上跑，
而"下架"这个动作在第一轮**只对 ADMIN 资源可用**，ADMIN 资源没有关系、也没人会去点它的详情直链。
三个动作把它挖出来：

1. **问"我声称的这句话覆盖了几个入口"**：需求是"用户端只展示上架状态的资源"，
   而我实测的只有 `/explore`。于是把**所有**取资源的调用点列出来
   （`getCityPack` / `getPois` / `getProducts` / `getPoiDetail` / `getProduct`），
   再逐个回到 Service 看有没有 `.eq(status, 1)` —— 两个 `selectById` 立刻露出来。
2. **读注释时顺手核代码**：`getPoiDetail` 的注释写"目标被下架或删除时跳过"，
   而下一行只判了 `target == null`。**注释比代码"先进"，本身就是信号** ——
   这个仓库注释密度高是刻意的，所以注释与代码不一致时，八成是代码没跟上意图。
3. **问"调用方是谁"再动手**：加 status 过滤前先 `grep getPoiDetail`，
   确认只有 Controller 在调、没有内部模块依赖它返回下架资源 —— 否则这一改会改坏别的模块。

第 3 条也解释了为什么这两个缺口能存活到 M10：`getPoiDetail` 一直是**纯游客入口**，
在"运营能下架资源"这件事出现之前，**没有任何路径能产生 `status=0` 的行**。
M10 第一次让 `status=0` 成为可达状态，缺口才从"理论存在"变成"点得进去"。
