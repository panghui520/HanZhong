## 一、模块职责边界

**做**：把 `citypack/hanzhong/` 的公开语料（11 篇城市知识 + 42 个资源点 + 14 项乡村体验
+ 16 款乡村产品）切片、向量化、建索引；对用户提问做**混合检索**（向量召回 ∪ BM25 召回）；
**知识库覆盖不到的问题明确拒答**；命中时拼装上下文交给大模型生成，SSE 流式返回；
前端展示答案、回答模式、知识来源（含原文链接）、检索条数与相关度。

**不做**：不做业务数据查询（那是 M4/M5/M7 的规则与 SQL）；不连业务库；
不做多轮对话记忆（服务端无状态，上下文只在浏览器里）；不做文档上传管理后台
（语料来自 `citypack/`，由构建脚本读取，不走 HTTP 上传）。

**三条设计红线没有被触碰**：

1. 不新增任何电商入口 —— 问答只引用已有 POI / 体验 / 产品的公开描述，页面上没有加购按钮。
2. **页面刻意不叫「AI 助手」**，叫「文旅知识问答」。定位是**知识服务入口**，
   不是聊天机器人：首屏是「先查过资料，再开口回答」+ 覆盖范围统计 + 知识卡片，
   提问后才收成流式对话区。
3. RAG / 向量库 / SSE 都是实现手段。页面上不打「基于 RAG 技术」这类标签，
   讲的是"回答只依据知识库，超出范围会直说"。

## 三、接口定义

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/ai/qa` | **SSE 流式问答**。事件序列 `meta → delta×N → done`，出错发 `error` |
| GET | `/api/ai/health` | 知识库状态：切片数、文档数、向量化实现、词表规模、回答模式、缓存条数 |
| GET | `/api/ai/suggestions` | 推荐问题。知识库不可用时返回**空数组**（不是报错），前端隐藏推荐区 |

以上三个都由 Java `AiController` 代理转发到 Python 服务（`http://127.0.0.1:8000`），
内部调用带 `X-Internal-Token`。Python 服务不可达时：

- `/api/ai/qa` → HTTP 200 + `error` 事件（"AI 服务未启动或端口不通…"）
- `/api/ai/health` → `code: 3001`（"AI 服务不可用，请确认 server-ai 已启动"）
- `/api/ai/suggestions` → `code: 0` + 空数组

**为什么用 POST + fetch 自己解 SSE，而不是 `EventSource`**：`EventSource` 只支持 GET，
问题得塞进查询串 —— 中文要编码、长问题会撞 URL 长度上限，而且会被浏览器历史与
反向代理记下来。用 POST 语义更对，代价是自己写 SSE 分帧（封在 `api/ai.ts` 里）。

## 四、两个 API Key 填在哪里

**对话模型与嵌入模型必须分开配凭证。** 这一条不是风格问题，是硬约束：
DeepSeek 官方只提供 `chat/completions`，**没有 `/embeddings` 端点**（已查证官方文档）。
若沿用 `LLM_BASE_URL` + `LLM_API_KEY` 去调嵌入，请求会打到
`https://api.deepseek.com/v1/embeddings` 并返回 404。

根目录 `.env`（**只被 Python 读**，Java 不读）：

| 行 | 变量 | 填什么 |
|---|---|---|
| 17 | `LLM_API_KEY` | DeepSeek 的 key（对话） |
| 29 | `LLM_EMBEDDING_API_KEY` | 硅基流动的 key（嵌入） |

`LLM_EMBEDDING_MODEL` 已预填 `BAAI/bge-m3`，`LLM_EMBEDDING_BASE_URL` 默认
`https://api.siliconflow.cn/v1`。

**为什么选 `BAAI/bge-m3`（1024 维）而不是 `Qwen/Qwen3-Embedding-8B`（4096 维）**：
① 中文强且成熟；② **不需要指令前缀** —— Qwen3 系列是指令感知的，查询侧要加
`Instruct: …` 前缀才发挥最佳效果，而 `ApiEmbedder.embed()` 与 `embed_many()` 走同一条
路径，加前缀得改类；③ 向量在本项目只负责召回、排序交给 BM25，8B 的收益很小而
调用成本高一个量级。

⚠️ **`.env` 只被 Python 读**：`pom.xml` 没有 dotenv 依赖，Java 的 `application.yml`
全是 `${VAR:默认值}` 读**系统环境变量**。两边默认值恰好一致所以能跑通。
**在 `.env` 里改 `INTERNAL_TOKEN` 会让两边不一致，`/api/ai/**` 全部返回 3001。**

⚠️ **必须用 `server-ai/.venv/Scripts/python.exe`**：托管 Python 没装 `python-dotenv`，
而 `_load_dotenv()` 在 `ImportError` 时原本静默 `return`，表现为"填了 `.env` 但所有配置
都是默认值、零报错"。本轮已改为喊一次警告并打印 `sys.executable`。

### 5.2 检索通道消融与融合策略（26 条用例）

两组实验：`probe-channel-ablation.py` 量"每个通道单独能拿多少"，
`probe-fusion-ranking.py` 量"融合策略怎么选"。

| 策略 | top1 | top5 |
|---|---|---|
| BM25 单边（旧实现） | 20/26 | 26/26 |
| 纯向量（BAAI/bge-m3） | 22/26 | 25/26 |
| **RRF 融合（现实现）** | **23/26** | **26/26** |
| 加权归一化 w_bm25 = 0.3 / 0.5 / 0.7 | 22 / 21 / 19 | 26/26 |

两通道**互补 8 条**：向量独中 5 条（汉中在哪个省 / 汉中有什么值得带走的特产 /
汉中茶叶产区在哪 / 汉中仙毫多少钱 / 汉中哪里可以住宿），BM25 独中 3 条
（汉江发源于哪里 / 镇巴腊肉 / 汉中的非物质文化遗产），都不命中 1 条（留坝有什么民宿）。

**为什么选 RRF，而不是"纯向量"或"加权"**：

- 纯向量的 top1 更高，但 **top5 掉了一条** —— top5 决定喂给模型的上下文，
  不能降。RRF 是唯一"top1 提升且 top5 不降"的策略。
- 加权归一化随权重**单调变差**（w_bm25 从 0.3 加到 0.7，top1 从 22 掉到 19），
  说明 BM25 归一化分与余弦相似度**本来就不可比**，硬加权只是凭经验调参。
- RRF 只用两路的**名次**、不用分数，因此不必去解决"怎么把两种分数量纲对齐"
  这个没有正确答案的问题。实测 k 取 1/3/5/10/20/60 结果完全一致，
  所以用 RRF 原文默认值 `k = 60`，不引入需要额外解释的调参。

**这组数字推翻了一个原有设计前提**，详见第八节。

## 六、本轮修复的缺陷

### 6.1 ★ 向量通道在配了厂商嵌入模型后**从未生效**（最严重）

**现象**：换成 `BAAI/bge-m3` 后重建索引，检索指标与旧 ngram 基线**一字不差**
（top1 20/26、top5 26/26）。当时判断为"排序由 BM25 负责，所以向量换模型不影响排序"。

**真实原因**：`store._vector_candidates()` 调 `self.embedder.embed(question, restrict_vocab=True)`，
而 `NgramEmbedder.embed()` 有这个参数、**`ApiEmbedder.embed()` 没有** → 每次查询抛
`TypeError` → 被 `except Exception: return []` 吞掉 → 向量通道**一次都没生效**。

**为什么伪装得这么好**：设计上"向量只负责召回、BM25 负责排序"，所以向量失效后
结果看起来"还行"，只是没有增益。**只有做通道消融（纯向量 0/26）才暴露。**

**修法（两处）**：

1. `ApiEmbedder.embed()` 签名对齐 `NgramEmbedder.embed()`，接受并忽略 `restrict_vocab`
   （厂商模型词表固定且不可枚举，无法照做；BGE-M3 本身也不需要）。
2. `store._vector_candidates()` 的 `except` **不再静默**：新增 `_warn_vector_failure()`，
   记一条 warning 日志（同一原因只记一次，避免刷屏）。
   **降级本身是对的（外部依赖坏掉不该让整个请求失败），但降级必须是可观测的。**

**修复后回归**：混合检索 top1 仍 20/26、top5 26/26 —— 与修复前一致，无退化。

### 6.2 系统拒答自己推荐的问题

**现象**：首屏快捷问题「汉中的气候怎么样，什么季节去最合适？」被判
`no_answer`，`gaps=['最合适']`。**推荐你问、又拒绝回答**是最刺眼的缺陷。

**根因**：jieba 把 `最合适` 标成 `a`（形容词），语料里当然没有这个词。

**为什么没被测出**：`eval_retrieval.py` 原来的 26 条正例里**没有一条是推荐问题的写法**。

**修法**：① 新增 `NON_TOPIC_FLAGS` 词性黑名单（形容词/副词/代词/数词/时间词/
连词/介词/助词等）；② 评测脚本**新增第三段**「推荐问题不应被拒答」，
从 `cache/qa_demo.json` 的 `meta.suggestions` 读取，**与线上同源**。

### 6.3 反例漏过（"汉中有哪些上市公司"）

**根因**：原判据"任一 2 字子串命中即放过"被偶然的跨词片段骗过 —— `上市公司` 的
2 字子串 `市公` 来自语料中"城市公共…"。

**修法**：改为 `_composed_of_known()` —— 能拆成两段、且**两段都在语料里**才放过
（左段从 2 字起，避免单字碎片）。**反例漏过 1 → 0，且不影响 26 条正例。**

### 6.4 拒答文案显示 `hanzhong` 而非「汉中」

`qa.py` 用了 `settings.city`（编码）。新增 `settings.city_name` 属性，
从 `citypack/<city>/meta.json` 的 `name` 读中文名，取不到才退回编码。

### 6.5 jieba 启动日志噪声（13 行）

**根因**：`lexical._segment` 里是**函数内延迟导入** `import jieba`，而 jieba 的
`__init__` 会执行 `default_logger.setLevel(logging.DEBUG)` 并挂一个自带 handler。
所以在导入**前**设级别会被覆盖，在 `warm_up()` **之后**设又太晚
（噪声正是在建词典时发的）。

**修法**：`_quiet_jieba()` 内**先 `import jieba`**，再 `setLevel(WARNING)` +
`handlers.clear()` + `propagate=True`，并放在 `warm_up()` **之前**。
清 handlers 是因为 jieba 自带的 handler 没有 formatter，会导致每行日志出现两次。
**结果：13 行 → 5 行，jieba 噪声 0 条。**

### 6.6 `build_kb.py --api` 缺 key 时静默退回离线实现

建出来的库不是用户以为的那个，日志上只有签名不同。**修法**：退出码 2 + 明确提示
（"嵌入用硅基流动的 key，跟对话模型的 `LLM_API_KEY` 不是同一个"）。

### 6.7 相对路径按 CWD 解析

`.env` 里是 `data/vectorstore` 这种相对路径，`Path(...)` 按 CWD 解析。从 `server-ai/`
启动会去找 `server-ai/data/vectorstore`，然后报"知识库没构建"——**提示指向的方向是错的**。
**修法**：新增 `_path()`，相对路径按仓库根解析。

## 七、关键设计验证

### 7.1 拒答为什么不用相似度阈值（实测证据）

反例「汉中有地铁吗」的 `top_score = 0.543`，**比正例「朱鹮是在哪里发现的？」的
0.4191 还高**。六种分数型判据全部失效。所以改用"查询里的主题词在语料中是否
完全不存在"（`topic_gaps`），这是集合判定，不是阈值判定。

### 7.2 `jieba.cut` 与 `posseg.cut` 词边界不一致，不能互换

实测 22 条问句里 **3 条词边界不同**，且 posseg 会把领域词切碎
（"汉中仙毫" → "仙"/"毫"、"秦岭四宝" → "四"/"宝"）。
**所以边界仍由 `jieba.cut` 决定，只借 posseg 的词性**（`_pos_flags` 用 `setdefault`
保证外部词边界优先）。

### 7.3 collection 名带向量化实现指纹

`kb_city__api-BAAI-bge-m3`。换实现（或改别名表）会落到另一个集合，
不会把两种模型的向量混进同一个集合（Chroma 的集合维度是固定的，混进去会静默出错）。
`rebuild` 会顺手清掉本库里其他 `kb_city__*` 集合，不留孤儿。
**换模型不重建索引 → `count() = 0` → 报"还没有构建知识库"**（设计好的提示，不是故障）。

### 7.4 混合检索的分工

候选池 = 向量 top-pool ∪ BM25 top-pool（`MIN_POOL = 20`），同一篇文档只保留得分
最高的切片。语料 151 片、pool 取 20 时 top5 命中与全量 BM25 仍然一致；
语料再长大后 pool 才真正起到限流作用。

## 八、排序策略：从「BM25 单边」改为「RRF 融合」（已实施）

分工的原始依据是"向量分数受文档长度影响太大，实测比 BM25 差 6 条"——
**那是离线 ngram 实现的结论**。换成语义嵌入（`BAAI/bge-m3`）后实测（见 5.2）：
纯向量 top1 **22/26**，**反超** BM25 的 20/26，两通道互补 8 条。

也就是说"BM25 单边排序"拿不到向量独中的那 5 条。据此把排序改成 RRF 融合：

```python
# store.query()：两路各自算名次，融合分只用名次、不用分数
fusion[index] += 1.0 / (RRF_K + rank)      # RRF_K = 60
for index in sorted(fusion, key=lambda i: -fusion[i]): ...
```

**落地时的两个取舍**：

1. **`Hit.score` 的口径没有跟着改。** 它仍是 BM25 归一化分（前端"首条相关度"）。
   改之前专门量过：RRF 排序后首条的 BM25 归一化分落在 **19%~78%、没有一条为 0**，
   所以展示口径不需要动，前端零改动、零回归风险。排序键是新加的 `Hit.fusion`。
2. **`sources[].score` 因此不再单调递减**（第 3 条可能比第 1 条高）。前端不逐条
   展示这个分数（只用首条那个），保留它是为了排查时能看到每条的词法相关度。
   已在 `qa._sources_from_hits` 的 docstring 里写明。

**顺带删掉两处死代码**：`lexical.rank()` / `rank_all()` / `Scored`，以及
`LexicalIndex.doc_ids` / `chunk_ids` —— 它们的唯一读者就是被替换掉的
"纯 BM25 排序"路径，已无调用点。纯 BM25 的对比数据留在本节与 5.2，
需要时照数据重写即可，不必在代码里留一份跑不到的实现。

页面会显示成"79 篇城市知识"。新增 `by_type_docs`（按文档数），前端改用它；
侧栏的"切片 / 文档"仍用 `chunks` / `docs`，两个口径各归各位。

> **★ 2026-09-28 更新**：侧栏那块「知识库状态」已整块从游客端删除
> （见第 5.3 节后的复查表），所以"侧栏用 `chunks` / `docs`"这一句**在界面上已不成立**。
> `by_type_docs` 仍在用 —— 现在它服务的是**欢迎区的「覆盖范围」**与侧栏的

### 9.9 离线演示缓存同步（`qa_demo.json`）

断网或 `DEMO_MODE=true` 时，服务走的是**缓存回放**（`llm_enabled=False` → 查缓存 →
未命中才掉到摘录）。所以这份缓存就是现场演示的第一印象，**扩充语料后必须回头改它**。

扩充后它有三类问题：

| 问题 | 具体 | 处理 |
|---|---|---|
| **答案被自己的扩充证伪** | `cache-tiankeng` 写着「具体的分布点位、开放情况、游览方式在知识库中没有记载」；`cache-hanzhong-xianhao` 写着「关于茶叶的具体品质指标、工艺细节，当前知识库中没有记载」。这两句在写完 `11-tiankeng` / `10-hanzhong-tea` 之后**就是假的** | 两条答案**重写** |
| **来源列表指着旧文档** | 问「天坑群」的来源卡片指向只有一句话的 `04-ecology`；问「仙毫」指向 `07-local-products` | 逐条改到新文档（保持 ≤5 条，受 `MAX_SOURCES` 限制） |
| **最可能被问的主题没有缓存** | 美食、亲子、乡村体验、行程、景区怎么选 | 新增 **5 组** |

另外 `cache-products` 的答案原本答「值得带走」却列了矿产与玉石（**带不走**），
已重写为按「茶叶 / 粮油 / 腊味禽蛋 / 生鲜食用菌 / 中药材蜂蜜 / 文创非遗」分类。

**新增一道机器检查**（`scripts/check_demo_cache.py`）：缓存只存 `doc_id`，
来源名称与链接是**运行时**现查的 —— 这个设计本身是对的（改数据包不会留下过期链接），
代价是**语料改了而缓存没改不会有任何报错**，只会让来源卡片静默变空。
脚本现在逐个 `doc_id` 校验存在性，并顺带校验首屏 5 问命中。

**实测**（`DEMO_MODE=true`，独立实例跑在 8001，不影响 8000 的开发实例）：
**12/12** 通过 —— 10 个主题问题全部 `mode=cache` 且来源指向新文档，
2 条反例（「汉中有地铁吗」「汉中房价多少」）仍正确拒答。
缓存规模 **11 组 / 50 条问法 → 16 组 / 76 条问法**。

### 9.10 缺口判据的已知边界（`topic_gaps` 会漏过什么）

本轮给判据加了第 5 条（`_glued_with_function_word`），它是一条**放过**条件 ——
方向与判据原有的保守取向相反。10 条反例只能证明这 10 条没被放过，
证明不了这个形状在别处也安全，所以另写了 `scripts/eval_gaps.py`
（**51 条反例 / 30 条正例**，只依赖词法索引，秒级跑完）。

结果：**正例 30/30 全部放行**（新规则没有造成误拒），**反例漏过 6 条**。

| 反例 | 被哪个词放过 | 那个词凭什么算"语料里有" | 扩充前 df |
|---|---|---|---|
| 汉中的公交线路有哪些 | `公交线路`（拆成 `公交`+`线路`） | `doc:12-aviation`「机场大巴停靠点均为市区内**公交**车站站牌」 | `公交` **0 → 1** |
| 汉中高速路况怎么样 | `路况` | `doc:02-climate`「山区景区…需要特别留意**路况**」+ `doc:27-seasons` 三处呼应 | `路况` 1 → 4 |
| 汉中停车场收费吗 | `停车场` / `收费` | `doc:11-tiankeng`「建设服务保障点、**停车场**等设施」/ `doc:20-scenic-guide`「18 个**收费**或免费景区」 | 各 **0 → 1** |
| 汉中最近有什么新闻 | `新闻` | `doc:11-tiankeng`「陕西省人民政府召开**新闻**发布会」 | `新闻` **0 → 1** |
| 汉中明天天气怎么样 | `气候`（别名表把"天气"映射成"气候"） | `doc:02-climate` 等 13 片 | `天气` 0 / `气候` 13 |
| 汉中最近有什么活动 | `活动` | `doc:05-zhu-huan`「朱鹮**活动**区域」/ `doc:11-tiankeng`「龙门山**活动**构造带」 | `活动` 1 → 2 |

**归因是实测的，不是推断的**：用 `git archive 48519db~1` 导出扩充前的数据包，
跑同一套 `build_chunks` 对比 df —— `公交`/`停车场`/`收费`/`新闻` 四个词
确实是**这次扩充从 0 抬到 1** 的；`路况`/`活动` 扩充前就 > 0，`线路` 扩充前就是 5。

**也就是说：这 6 条里有 3 条是本轮扩充新引入的，3 条本来就在漏。**
成因不是第 5 条规则，而是判据第 3 条的口径本身 ——
它问的是"**语料写过这个主题没有**"，不是"**答得上没有**"。
一个词只要被顺带提过一次就算"写过"，而"停车场出现在『建设停车场等设施』里"
显然不构成对"停车场收费吗"的回答。

**试过收紧，否决了。** 把第 3 条的门槛从 `df > 0` 提到 `df >= 2`，直觉上正好干掉
上面这些 df=1 的漏网。**实测会误拒 4 条在覆盖范围内的问句**：

| 会被误拒的问句 | 主题词 | df |
|---|---|---|
| 汉中是什么时候解放的 | `解放` | 1 |
| 汉江发源于哪里 | `发源` | 1 |
| 汉中面皮是省级非物质文化遗产吗 | `省级` | 1 |
| 菜豆腐是什么？怎么做出来的？ | `出来` | 1 |

语料确实写了这四件事，只是各写了一次。**这个方向上没有安全的阈值**，
只有"放过真缺口"与"误拒真覆盖"两种代价；本项目选后者不可接受 ——
拒答自己答得上来的问题，是演示里最刺眼的缺陷。这两条结论都写进了
`lexical.py` 的 `topic_gaps` 文档串，避免以后有人再试一遍。

**也不为迁就判据去改语料。** 上面那几句（"公交车站站牌""收费或免费景区"）
都是自然、有用的表达，删掉是把工具的局限转嫁成内容的损失。

**改成的做法**：把边界变成**可执行的测试**而不是一段说明 ——
`eval_gaps.py` 里的 `KNOWN_LEAKS` 逐条记录"哪条漏了、被哪个词放过、为什么"，
并**精确比对实测结果**：多一条漏过就失败（判据被放松了），
少一条也失败（判据被收紧了，就该从表里删掉并回来改本节）。
这样这张表不会腐烂。当前退出码 0。

**反向脆弱点（记一笔）**：上表里 4 条"在覆盖范围内"的问句，
其主题词的 df **恰好是 1**。它们现在能过，靠的是语料里那一处孤证；
语料再改动时，这几个词是**往误拒方向翻车**的第一批候选。

## 十、问答架构：从「知识库回答器」改成「知识库增强的助手」（2026-09-26）

### 10.1 缺陷：把「知识库的覆盖范围」当成了「系统能回答的范围」

**实测现象**（改动前，未做任何修改就跑的）：

| 问题 | mode | 回答 | DeepSeek 调用 |
|---|---|---|---|
| 你是 AI 吗？ | `no_answer` | 知识库里没有关于「ai」的记载… | **没有** |
| 你是什么助手？ | `no_answer` | 知识库里没有关于「助手」的记载… | **没有** |
| 什么是 AI？ | `no_answer` | 知识库里没有关于「ai」的记载… | **没有** |

三条问题的 `retrieved` 都是 5 —— 检索发生了，但结果被丢掉，然后直接拒答。
DeepSeek 配了、也通，一次都没被调用。

**代码只有一行，但它把两件事混成了一件：**

```python
if gaps and not cached:
    mode = "no_answer"        # ← 缺口判定是**硬闸门**
```

`topic_gaps` 问的是"**语料写过这个主题没有**"。用它来决定"要不要回答"，
等于宣称"知识库没写过的话题，系统就答不了"——这对本项目恰好不成立：
DeepSeek 本来就能好好回答"什么是 AI"，而"你是 AI 吗"跟知识库毫无关系。

**被误伤的三类问题：**

1. 问系统自身 —— 你是 AI 吗 / 你是什么助手
2. 问通用概念 —— 什么是 AI / 什么是非遗
3. 本地事实但知识库没写 —— 汉中有地铁吗 / 汉中到西安的机票多少钱
   （这类**不该**一刀切拒答：应该由模型说清"知识库缺少哪部分依据"，
   再回答其中通用的部分）

### 10.2 改法：三条链路（`route`）取代闸门

`topic_gaps` 从**闸门**降级为**信号**：它只决定走哪条链路、用哪份提示词。

| `route` | 判定 | 检索 | 交给模型的上下文 | 来源卡片 |
|---|---|---|---|---|
| `rag` | 缺口判定没发现问题 | 是 | 命中的【资料】 | 有 |
| `constrained` | 涉及本地事实，但知识库**可能**没写过（`gaps` 非空） | 是 | 命中的【资料】+ **更严的提示词** | 有 |
| `general` | 与汉中无关（系统自身 / 通用概念 / 寒暄） | **不检索** | 无 | 无 |

有模型时，**三条链路都走模型**（`mode` 全是 `llm`）。不再存在"因为知识库
没写过就拒答"这条路 —— 事实约束从"一刀切拒答"移到了提示词里。

**`constrained` 照常把资料给模型**，这一点是被实测逼出来的：缺口判定会**误报**
（51 条检索用例里有 3 条被误判成有缺口，例如"浆水面为什么叫浆水面"，
jieba 把领域词切碎成了"叫浆"）。如果 `constrained` 干脆不给资料，
这些本来答得上来的问题会被提示词劝退。所以它的措辞是"资料**可能**答不了"，
并要求模型"**先看【资料】能不能回答**"。

### 10.3 判定顺序本身就是设计（换一下就出 bug）

```
① 提到城市名？          → 本地问题：有缺口 constrained / 没缺口 rag
② 像在问系统自身或通用概念？ → general
③ 其余                  → 按本地问题保守处理：constrained / rag
```

顺序不能换，两条理由都是实测抓出来的：

- **城市名必须最前**，否则"汉中有 AI 产业吗"会因为带 `ai` 被送进 `general`，
  而它点名了汉中，必须按本地事实处理。
- **通用问题的识别必须排在缺口判定之前**。反例是 `你是谁？`：分词后没有一个
  长度 ≥2 的实词 → `gaps=[]` → 若先看 gaps 就会被当成"知识库覆盖"送去检索，
  实际表现是**拿午子仙毫 / 羌衣香包 / 段木香菇去回答"你是谁"**（改动过程中真出现过）。
- **③ 一律保守**：识别不出来就当本地问题。"有恐龙化石吗"落在这里 ——
  在汉中旅游站里问，几乎一定是在问汉中。误判成 `general` 的代价是
  "该守事实约束时没守"，比反过来严重得多。

### 10.4 `route` 与 `mode` 的职责分离

两者**正交**，混在一起正是原缺陷的来源：

| 字段 | 回答的问题 | 取值 |
|---|---|---|
| `route` | 模型被允许用**哪一部分知识** | `rag` / `constrained` / `general` |
| `mode` | 这条回答**实际由谁产出** | `llm` / `cache` / `extractive` / `no_answer` |
| `generator` | **真的调模型了吗** | 模型名（`deepseek-chat`）/ `cache` / `extractive` / `none` |

新增 `generator` 是为了让"到底有没有调 DeepSeek"成为一个**可直接断言的字段**，
不必从回答文本里猜（措辞和长度都会骗人），也不必去翻日志。

`no_answer` 的口径随之收窄：它现在**只**表示"离线演示模式下、这一问本来需要模型"。
配了模型时不会出现。

| # | 问题 | 链路 | 真的调了 DeepSeek | 检索 | mode | 来源 |
|---|---|---|---|---|---|---|
| 1 | 你是 AI 吗？ | `general` | 是（`generator=deepseek-chat`） | **0 条** | `llm` | 0 条 |
| 2 | 你是什么助手？ | `general` | 是 | **0 条** | `llm` | 0 条 |
| 3 | 什么是 AI？ | `general` | 是 | **0 条** | `llm` | 0 条 |
| 4 | 汉中有哪些好吃的？ | `rag` | 是 | 5 条 | `llm` | 5 条 |
| 5 | 汉中有哪些乡村体验？ | `rag` | 是 | 5 条 | `llm` | 5 条 |

回答摘录：

- 「你是 AI 吗？」→ "是的，我是 AI 助手，专门用来回答问题、提供信息。"
- 「你是什么助手？」→ "我是「汉游智脑」的助手，主要面向汉中文旅场景…"

  **知识库里能定位到的餐饮点非常少**…"（先讲资料里有的，再明说哪部分查不到）

**来源卡片仍然只来自元数据**：五条里有来源的 2 条，链接只出现

以及"数据包自有（无外链）"。`general` 那条**一张来源卡片都没有** ——
它没检索，署名一份没用上的资料等于把"可追溯"变成"看起来可追溯"。

### 10.6 边界用例（6 条）

| 问题 | 链路 | gaps | 表现 |
|---|---|---|---|
| 朱鹮是在哪里发现的？ | `rag` | 无 | 正常回答，带 detail 档深链 |
| 你是谁？ | `general` | 无 | 检索 0 条、来源 0 条（顺序修好之前它是 `rag`，会拿香菇回答"你是谁"） |
| 汉中有地铁吗？ | `constrained` | `地铁` | "知识库里缺少这方面的可靠依据…资料中没有提到任何城市轨道交通" |
| 汉中到西安的机票多少钱？ | `constrained` | `机票` | 明说资料只有通航方向、**没有票价**；顺带提示西成高铁 |
| 有恐龙化石吗？ | `constrained` | `恐龙` | 说没有可靠依据，并指向资料里真实的镇巴古生物化石 |
| 汉中为什么叫汉中？ | `rag` | 无 | 因汉水得名；对更细的词源明确表示不推测 |

第 3~5 条是 `constrained` 的价值所在：**模型拿到了资料、也守住了事实约束，
没有编造本地事实。** 这正是原实现想用"拒答"达到的目的，
但代价是把能答的也一起拒了。

### 10.7 离线（`DEMO_MODE=true`）下的三链路矩阵

有模型时三条链路都是 `mode=llm`，一片祥和；**降级路径必须单独实测** ——
断网是比赛现场的真实风险。

| `route` | 缓存命中 | 缓存未命中 |
|---|---|---|
| `rag` | `cache`（有来源） | `extractive`（摘录原文，有来源） |
| `constrained` | `cache`（有来源） | `no_answer`（说明离线边界，**无**来源） |
| `general` | `cache`（有来源） | `no_answer`（说明离线边界，**无**来源） |

实测 12 条全部符合：3 条 `general` → `no_answer` / 检索 0 / 来源 0；
7 条 `rag`（含首屏 5 条推荐）→ 全部 `cache`、来源 1~4 张；
2 条 `constrained` → `no_answer`、来源 0 张。

**离线文案也变了**（这是这次改动可见的成果之一）：

- 改前：「你是 AI 吗」→ "知识库里没有关于「ai」的记载"（答非所问）
- 改后：→ "当前处于离线演示模式（未配置大模型），我只能回答知识库覆盖的汉中问题。
  / 当前知识库覆盖汉中的地理气候、历史文化、生态与物产等公开资料，
  以及 42 个资源点、14 项乡村体验、16 款乡村产品。/ 你可以试试下面这些问题：…"

`constrained` 离线时 `retrieved=5` 但来源 0 张 —— 有意的：那些切片**没有被用来
回答**（回答是离线边界说明），给出来就是署名没用上的资料。

### 10.10 新增的回归脚本 `scripts/eval_routes.py`

`_route` 判错在两个方向上都是**静默**的（接口照样 200、照样流式吐字），
只有逐条看 `route` 才发现。所以把"分流对不对"变成可执行的测试：
它只依赖本地词法索引，**毫秒级、不花钱**，可以把已有全部用例一次扫完。

| 集合 | 条数 | 期望 | 实测 |
|---|---|---|---|
| `eval_retrieval.CASES` | 51 | 全部 `rag` | 50 `rag` + 1 已知误报 |
| `eval_retrieval.SUGGESTION_FALLBACK` | 5 | 全部 `rag` | 5 `rag` |
| 范围内压测 | 30 | 全部 `rag` | 30 `rag` |
| 反例（`NEGATIVE` + 超纲压测） | 54 | 无 `rag` | 48 `constrained` + 6 `rag`（全部为已知漏过） |
| 必测 5 条 | 5 | 见 10.5 | 全部符合 |

两张"已知偏差"表都做**精确比对**（沿用 `eval_gaps.py` 的纪律）：

- `KNOWN_LEAKS`（6 条，来自 `eval_gaps`）：缺口判定**漏过** →
  没有 gaps → 走 `rag`。既成边界，不是本次改动引入的，放行；追责在 `eval_gaps.py`。
- `KNOWN_MISROUTES`（1 条）：缺口判定**误报** → 本该 `rag` 却走 `constrained`。
  当前只有 `浆水面为什么叫浆水面`（jieba 把「浆水面」切碎，动词「叫」和
  碎片「浆」粘成「叫浆」）。影响有限：`constrained` 照样给资料、照样要求
  "先看资料能不能回答"，答案仍然对，只是提示词更严。

多一条失败（分流被改坏），少一条也失败（修好了，该把这行删掉）。

### 10.11 本节的已知边界（诚实清单）

- **`_looks_like_meta_or_concept` 是"窄识别"**：`META_WORDS` 是硬编码词表。
  没被识别出来的"系统自身"问法（例如"你会写诗吗"）会落到 ③ → `constrained`，
  于是会先检索一次、再给一份更严的提示词。**表现仍然正常**（模型照样回答），
  只是多一次无用的嵌入调用。宁可这样，也不要放宽识别去误伤本地问题。
- **`有恐龙化石吗` 走 `constrained` 而不是 `general`**：没有城市名、也不像通用概念，
  按 ③ 保守处理。这是**有意的选择**，不是遗漏。
- `KNOWN_MISROUTES` 那 1 条要靠改分词器才能消掉，本轮不动。
