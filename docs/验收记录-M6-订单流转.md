# M6 订单状态流转细化 + SQL 幂等化 + 顶栏订单入口 · 验收记录

> 对应需求（2026-09-25 提出）：
> 1. `db/` 下的 SQL 每次重跑都丢数据 —— 要求**结构与数据都不丢**；
> 2. 农产品发货流程要按正规电商流程细化（购物车结算 → 支付 → 待发货 → 物流 → 收货 → 评价，全程可退款）；
> 3. 首页/导航栏缺少醒目的「我的订单」入口。
>
> 本文是这三条需求的验收记录。M6 模块**第一版**（两态订单 + 探索页改版）的记录见
> `docs/验收记录-M6.md`，那一版里"订单状态只有两个"的结论**已被本文取代**。

## 二、订单状态机（七态）

```
                      ┌── 30 分钟未付款（定时任务）──▶ CANCELLED 已取消
                      │
PENDING_PAYMENT 待付款┤
                      └── 付款 ──▶ PENDING_SHIPMENT 待发货
                                        │        │
                                        │        └── 申请退款 ──┐
                                        │ 运营发货              │
                                        ▼                     ▼
                                   SHIPPED 已发货 ──┐   REFUND_REQUESTED 退款中
                                        │           │        │
                                        │           │        ├─ 同意 ─▶ REFUNDED 已退款（终态）
                                        │ 确认收货   │        └─ 拒绝 ─▶ 退回申请前的状态
                                        ▼           │
                                   COMPLETED 已完成  ┘（已发货也能申请退款）
                                        │
                                        └── 评价（星级 1–5 + 文字 + 图片 ≤3 张）
```

### 各状态的名称、流转条件与异常分支

| 状态 | 中文名 | 进入条件 | 可做的操作 | 异常分支 |
| --- | --- | --- | --- | --- |
| `PENDING_PAYMENT` | 待付款 | 提交订单即进入，同时写入 `pay_deadline = now + 30min` | 付款、取消 | 超 30 分钟未付 → `CANCELLED(TIMEOUT)`；付款时若已过期 → 报 **6013** 并顺手改成已取消 |
| `PENDING_SHIPMENT` | 待发货 | 付款成功 | 申请退款 | 未付款的单不能确认收货/退款/评价（一律 6006） |
| `SHIPPED` | 已发货 | 运营填写物流三要素后发货 | 确认收货、申请退款 | 物流三要素缺任一项 → 6009；重复发货 → 6006 |
| `COMPLETED` | 已完成 | 用户确认收货 | 评价 | 重复确认收货 → 6006；已退款/已取消的单不能评价 |
| `CANCELLED` | 已取消 | 待付款时用户主动取消，或超时自动取消 | 无（终态） | 已取消不能付款 → 6006。`cancel_reason` 区分 `USER` / `TIMEOUT` |
| `REFUND_REQUESTED` | 退款中 | 待发货或已发货时申请退款（理由必填） | 无（等运营） | 退款中不能再次申请、不能确认收货 → 6006；理由为空 → 6014 |
| `REFUNDED` | 已退款 | 运营同意退款 | 无（终态） | 已退款不能评价 → 6006 |

**两条设计取舍（答辩要能说清）**

- **只用一个 `status` 字段表达"退款中"，不另设 `refund_status` 列。** 两列表达同一件事，
  迟早有一天对不上。代价是要记 `status_before_refund`，否则"拒绝退款"不知道退回哪里。
- **能申请退款的是 `PENDING_SHIPMENT` 与 `SHIPPED` 两态。** 待付款还没付过钱，取消即可；
  已完成/已取消/已退款都是终态。

## 四、关键设计验证（都是实测，不是"应该没问题"）

### 1. SQL 幂等：三遍执行，快照一模一样

```
BEFORE: user=4 poi=42 exp=14 prod=16 banner=4 img=1 orders=37 items=37 review=9 cart=0 code=4
AFTER1: user=4 poi=42 exp=14 prod=16 banner=4 img=1 orders=37 items=37 review=9 cart=0 code=4
AFTER2: user=4 poi=42 exp=14 prod=16 banner=4 img=1 orders=37 items=37 review=9 cart=0 code=4
```

6 个文件退出码全为 0，唯一输出是 V6 那句设计好的 `note`（索引已存在，跳过）。

**MySQL 8 不支持 `ADD COLUMN IF NOT EXISTS`**（那是 MariaDB 语法）。V6 用临时存储过程查
`information_schema.COLUMNS` 再 `PREPARE/EXECUTE` 动态执行，用完 `DROP PROCEDURE`。
不这么做的话，第二次执行会报 `Duplicate column name` 而**中断**，文件后半段静默不执行 ——
在"整个文件一起执行"的场景下，比报错本身更危险。

**幂等的代价（写进文件顶部了）**：`CREATE TABLE IF NOT EXISTS` 遇到已存在的表只跳过、
不补字段，所以**今后表结构演进只能新开 V 文件写 `ALTER TABLE`**，改老文件不会生效。

### 2. `available_actions` 由服务端算（不是前端映射表）

`OrderVO.availableActions` 与 `statusLabel` 一样由服务端给出。前端只做
`actions.includes('PAY')`。前端若自己维护"状态 → 按钮"的映射表，加一个状态就要改两处，
迟早漏掉某处 —— 而漏掉的后果是**按钮该出现时没出现、该消失时还在**（用户点了才报错）。
已评价时服务端会把 `REVIEW` 从可选操作里去掉（状态没错，但"能做什么"变了）。

### 3. 运营端排序不能靠 `orderByAsc(status)` 的字母序

旧实现注释写着"待发货优先"，它当时确实成立，但**纯属巧合**：状态只有两个时
字母序里 P 在 S 前面。七态下字母序是 `CANCELLED, COMPLETED, PENDING_PAYMENT,
PENDING_SHIPMENT, REFUNDED, REFUND_REQUESTED, SHIPPED` —— 待发货掉到第 4 位，
退款中埋在下面，"优先"静默失效。改成 Java 里显式 `actionPriority()`：
待发货 0 / 退款中 1 / 待付款 2 / 已发货 3 / 终态 4。

### 4. `payOrder` 刻意不加 `@Transactional`

"已过期 → 顺手改成已取消 → 抛异常"这个分支需要在抛异常之后**仍然保留**已写入的状态。
被事务包着会一起回滚，结果是"提示已超时、刷新还是待付款"，用户反复点付款。
实测：过期后调付款接口返回 6013，随后 `GET /orders/{id}` 读到 `CANCELLED` + `TIMEOUT`。

### 5. `updateById` 默认忽略 null，所以"清空上次拒绝理由"必须用 `UpdateWrapper`

MyBatis-Plus 的 `updateById` 会跳过 null 字段。重新申请退款时要清掉上一次的
`refund_reply` / `refund_handled_at`，用 `updateById` 会**静默失效** ——
页面上同时出现"退款中"和上次的拒绝理由，自相矛盾。改用
`mapper.update(null, Wrappers.<Order>lambdaUpdate().eq(...).set(col, null))`。
实测：拒绝 → 再申请后 `refund_reply` 为空。

### 6. 评价的校验顺序：先问"能不能评"，再问"内容填了没"

第一轮验收脚本抓到：对一笔**待付款**订单评价，返回的是 `6012 请写点评价内容`
而不是 `6006 状态不允许`。根因是先校验评价内容、后校验订单状态。
后果是用户以为是自己内容没填好，反复改文案 —— **答非所问**。
已把 `requireOwnOrder` + 状态校验提到方法最前。

### 7. 评价图片：库里存 JSON 数组字符串，出库拼成完整 URL

- 不用逗号分隔：文件名里可能出现逗号，逗号分隔会静默劈开一个文件名。
- 一单一评靠 `order_review.uk_order` 唯一键兜底（先查只为给友好错误码，真正防重靠唯一键）。
- **图片上限必须落服务端**：前端限 3 张只是体验。接口是公开的，绕过页面能塞 50 张。
  服务端 `normalizeImages()` 去空、去重、挡 `..` 与非法字符（正则 `[A-Za-z0-9._/-]+`）、截到 3 张。
  实测：传 `["../../etc/passwd","ok/1.png","ok/1.png","ok/2.png","ok/3.png","ok/4.png"]`
  得到 3 张、无 `..`、无重复。
- **出库拼成 `/api/media/...`**（与 `PoiImageVO` 同一约定）。只给相对路径的话前端得自己
  知道前缀，前缀一改就两头不同步。方向上的不对称是刻意的：**提交时传相对路径**
  （服务端要拿它做穿越校验，不能让客户端自由拼前缀），**读取时给完整 URL**。

### 8. 定时任务用 `fixedDelay` 不用 `fixedRate`

`@Scheduled(fixedDelay = 60_000, initialDelay = 30_000)`。`fixedRate` 会在某次扫描
超时后重叠执行，白耗连接。批量一条 UPDATE 取消（不逐个改，避免"扫了一半"）。
日志里的分钟数从 `OrderService.payWindowMinutes()` 取，**不写死 30** ——
改了规则而日志还印旧数字，排查的人会照着错的数去算。单机假设已写进注释。

### 9. 倒计时到点后前端不自作主张改状态

真正的取消由服务端每分钟一次的任务执行，最多晚 60 秒。前端若自己把状态改成"已取消"，
页面显示已取消而库里还是待付款，刷新就打脸。所以到点只是停掉付款按钮、提示
"订单即将自动取消"，并给一个「刷新状态」按钮，状态一律以服务端回读为准。

### 10. 结算成功后直接落到订单详情，而不是订单列表

下单后进入的是「待付款」，用户此刻唯一想做的事就是付款。把他丢到列表里再找一次
"付款"按钮是多余的一步。详情页有倒计时，也能说清"超时会自动取消"。

### 11. 顶栏角标口径：`pending` 而不是 `total`

`GET /api/orders/count` 返回 `{total, pending}`。`pending` = **需要用户动手**的订单数
（待付款 + 已发货）。已完成的订单用户无事可做，算进角标会让角标只增不减，
变成一个永远消不掉的红点，用户很快就不再看它。退款中也不含：那在等运营，不是等用户。

## 六、踩过的坑（写下来避免重复）

### 1. 验收脚本的断言本身会写错，且错法不止一种

- **按固定下标取卡片**：`document.querySelectorAll('.card__title')[3]` 取到的是「收货信息」
  而不是「我的评价」—— 因为发货过的单会多一张「物流信息」卡，下标整体错位。
  改成**按标题文字找**。
- **用正则匹配整段卡片文字判倒计时**：`\d{2}:\d{2}` 会匹配到卡片上印的
  `2026-09-25 20:02`，于是断言永远为真。改成判断 `.cd` 元素在不在。
- **选择器不够具体**：`.badge-wait, .badge-sim` 先匹配到 AdminLayout 顶栏的
  "仿真数据"徽标（文档顺序在前），断言变成永远为真。改成限定在 `.aorders__meta` 里。

三条都是"断言通过了但什么都没验到"或"断言失败但代码没问题"，方向相反、危害相同：
**必须让失败的断言能被解释清楚，而不是急着改代码。**

### 2. 用运营令牌读用户订单会得到 6005

探针里 `api('GET', '/orders/{id}', undefined, admin.token)` 报了 6005。
那不是 bug —— `/api/orders/{id}` 只让本人看自己的单（不泄漏"这个单号存在"）。
读订单要用**下单人的令牌**。

### 3. 发货接口的响应是「运营视角」

`shipOrder` 用 `reloadAsAdmin` 回读，所以响应里的 `available_actions` 是运营能做的事
（已发货后运营无事可做 → 空数组）。第一轮我按用户视角断言，判成失败。
用户能看到什么，必须用 `GET /orders/{id}` 再查一次。**这两件事很容易搞混。**

### 4. V6 第一遍执行"退出码非 0"是假警报

管道里 `grep -v Warning` 无匹配会返回 1，`$?` 取到的是 grep 的退出码而不是 mysql 的。
核对 `information_schema` 后确认 13 列、新索引、`order_review` 表全部到位，存储过程已清理。

### 5. `input[type=file]` 处理完必须清空 `value`

否则用户再选**同一个文件**不会触发 `change` 事件，看起来像"点了没反应"。

### 6. `pay_deadline` 是 `LocalDateTime`，不带时区

序列化成 `2026-09-25T19:47:12`。按 ECMAScript 规范这种"日期+时间但无偏移"的形式
按**本地时间**解释，正好与后端一致。若写成 `new Date(iso + 'Z')` 会平白差 8 小时，
倒计时显示成 8 小时后。

## 七、已知限制（答辩时不能含糊）

1. **支付是演示级**：不接真实支付通道，"付款"就是用户点一下按钮，没有支付单、
   没有回调确认。真实实现应该是"创建支付单 → 等回调 → 幂等更新"。
2. **物流是手工填写的**：系统**不查询**任何快递公司接口，快递单号只用于说明流程，
   拿去官网查不到件。预计到达天数是运营填的数字，不是物流公司给的。
3. **退款不涉及真实资金**：同意退款只是把状态改成 `REFUNDED`，没有调用任何退款接口。
4. **定时任务是单机假设**：`@Scheduled` 在单实例下正确；多实例部署需要分布式锁，
   否则同一单会被多个实例重复取消（虽然重复取消是幂等的，但会多打日志）。
5. **超时取消最多晚 60 秒**：扫描周期是 1 分钟，所以 `pay_deadline` 过后订单不会
   立刻变已取消。用户此时点付款会拿到 6013 并被顺手取消。
6. **没有商户角色**：需求里的"商户可查看已发货信息并确认收货"由**用户本人**完成。
   本项目没有商户表，红线也写明"无店铺、无商家"—— 农产品挂靠体验或产地，
   不存在独立的商家主体。
7. **评价不可修改/删除**：一单一评，提交后不能改。真实电商通常允许追评或删除。
