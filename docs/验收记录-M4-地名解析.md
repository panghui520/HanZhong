## 一、用户报的现象与根因

**现象**：用户问「汉中高铁站附近有哪些酒店」，得到 12 张卡片，全部在**洋县**
（洋县洁岩时尚宾馆、凤来祥宾馆、洋县华琳大酒店……），距离是"相对洋县高铁站"的。
助手在回答开头如实说明了"实际定位到的搜索中心是洋县高铁站"，但用户要的是汉台区。

**根因不在提示词、不在模型，在 `amap.geocode()` 这一步**：
高德地理编码对「汉中高铁站」返回两条候选，**第一条是「洋县高铁站(公交站)」**
（洋县也通高铁，名字里同样带「高铁站」），而当时只取了第一条。

### 实测对照（2026-09-26，高德 Web 服务）

| 查询 | `geocode/geo` 首条 | `place/text` 首条 |
|---|---|---|
| 汉中高铁站 | ❌ 洋县高铁站(公交站) `107.525665,33.226810` | ✅ 汉中站（汉台区）`107.029962,33.090721` |
| 汉台区 | ✅ 汉台区 `107.032010,33.067523` | ✅ 汉台区 `107.032010,33.067523` |
| 宁强县 | ✅ 宁强县 `106.257636,32.830032` | ✅ 宁强县 `106.257636,32.830032` |
| 汉中火车站 | ⚠️ 退化成「陕西省汉中市」（市级，level=市） | ✅ 汉中站（汉台区） |

**结论：`geocode` 擅长行政区划、不擅长口语地名；`place/text` 反过来。**
所以不选一个，而是按地名形态分工。

## 二、设计

### 2.1 三级解析（`places.PlaceResolver.resolve`），顺序不可换

| 级 | 手段 | 命中什么 | 为什么在这一级 |
|---|---|---|---|
| ① | **本地地名表** `citypack/hanzhong/places.json` | 11 个区县 + 别名 + 地标 | 零网络、零成本、结果确定；断网演示仍可用 |
| ② | **高德 `place/text`** | 口语地名（汉中高铁站 / 石门栈道 / 青木川） | 搜的是"地点"不是"地址"，对口语名最准 |
| ③ | **高德 `geocode`** | 行政区划、规范地址 | 对口语地名最不准（就是本次的坑），所以放最后兜底 |

**一级只做精确匹配**（含别名与行政区前缀剥离 `陕西省`/`汉中市`），**刻意不做包含匹配**：
「洋县高铁站」包含「洋县」，按包含匹配会落到洋县区县中心，而用户要的是那个车站。
这类"更具体的地名"必须交给二级去搜。

### 2.2 相关性校验（`_relevant`）—— 一个必须补的防线

`place/text` 与 `geocode` 都是**模糊**的：查不到时照样返回结果。实测：

- `search_text("不存在的地方xyz")` → 首条「一个嗦粉的地方（汉台区）」
- `geocode("不存在的地方xyz")` → 「陕西省汉中市镇巴县小洋镇」

不挡的话，"用户打错了一个字"会被静默变成"一个随机的真实地点"，而且带着
看似合理的地址与距离，用户无从分辨。判据选得**简单且可解释**（不引分词依赖）：

> 一方包含另一方，**或查询词的前两个字出现在结果名里**。

为什么用"前两字"而不是"任意公共子串"：`不存在的地方xyz` 与 `一个嗦粉的地方`
的公共子串是「地方」—— 长度 2 就通过，等于没挡。查询词的**开头**才代表用户在指哪儿。

二级搜索是**逐条**校验、取第一个相关的（不是只看首条）：高德按热度/距离排，
不按字面匹配度排，"首条不相关、次条相关"是常见情形。

## 五、已知边界（未修，写清楚）

1. **本表只覆盖汉中的 11 个区县 + 汉中站**。用户说"汉中某某小区""某某路口"这类
   极小地名，仍走高德，可能落到相近的地方 —— 这类地名本来就没有权威数据源。
2. **高德偶发超时**（实测 8 秒超时多次触发）。表现为工具错误 + 前端失败态，
   **不会给出假结果**。是否加大 `AMAP_TIMEOUT_S` 或加重试，留待观察。
3. **相关性校验是启发式**：`汉中` 查 `汉中某某酒店` 会通过（前两字命中）。
   对"中心点"这个用途足够，但它不是实体消歧。
4. 别名表刻意**不放裸的「高铁站」「火车站」「市中心」**：洋县、佛坪、宁强都有
   高铁站，裸词在那些语境下会被误解析成主城区。

## 六、本轮未做

**两日游 / 三日游线路规划**（用户同时提出的需求）。现状：问「帮我规划一个汉中两日游」
会走 `knowledge_search`，命中数据包的 `26-itinerary` 文档，得到的是**排行程的原则与
一个参考框架**（"先按方向分组、一天累计超过 360 分钟基本装不下"），
而**不是针对用户需求的成行方案** —— 助手还会主动说"知识库里缺少'两日游'这个说法的
直接依据"。用户的感觉是"说不明白"，这个判断是准确的。

数据包已具备做真行程规划的条件（42 个 POI，含 `district` / `lng,lat` /
`duration_min` / `level` / `tags` / `scene`），但需要新增一个 `plan_itinerary`
工具把"方向分组 + 时长预算"从**知识文档里的原则**变成**代码里的算法**，
属于新功能而非修复，见 `docs/M4-第一阶段设计分析.md` 的后续阶段表。
