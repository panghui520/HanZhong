# M2 乡村体验与农产品 · 验收记录

> 验收日期：2026-09-23 · 结论：**通过**
> 模块范围：`db/V2__m2_experience_product.sql` → Spring Boot 接口 → 详情页与首页 → 联调

## 一、模块职责边界

**做**：`experience` 乡村体验、`product` 乡村农产品、`product_category` 分类三张表；
导入器在读取阶段把产品的中文分类名解析成编码并做引用自检；
前端详情页的「乡村体验 / 乡村好物」与首页好物切到后端，并删掉本地 JSON 那条链路。

**不做**：订单、购物车、支付、库存扣减（M6）；行程编排（M4）；承载统计（M5）。
`product.stock` 只存不扣——扣减是下单时才发生的事。

**这条模块的核心是一句设计红线**：产品不是独立商品，必须挂靠一次体验或一个产地资源点。
它落在 `product` 表的 `CHECK (poi_id IS NOT NULL OR experience_id IS NOT NULL)` 约束上，
而不是只写在文档里。库里不可能存在"孤立商品"，前端也就没有独立商城页面的数据基础。

## 五、前端改动

| 改动 | 原因 |
|---|---|
| `citypack.ts` 的 `getExperiences` / `getProducts` 切到后端 | M2 的数据源落点。函数名与返回结构不变，所以调用页面基本不用动 |
| 新增 `getExperience` / `getProduct` / `getProductCategories` | M4 选点、M6 下单、首页筛选条要用；接口先留，页面后接 |
| 新增 `query()` 拼查询串 | 值为 `undefined` 的键直接丢掉，避免拼出 `?poi_id=` 这种空参数 |
| **删除 `loadLocal`、`DATA_BASE`、`cache`** | 本地 JSON 这条链路整条移除，不留两套数据源 |
| **删除 `scripts/sync-citypack.mjs` 与 `web/public/data/`** | 它们只服务于上面那条链路，留着就是"接口改了、本地文件没改"的静默不一致 |
| `web/package.json` 去掉 dev/build 里的同步步骤 | 构建不再依赖脚本生成的文件 |
| `PoiDetail.vue` 的体验与产品改为按 `poi_id` 从后端取 | 原来取全量列表再在前端 filter，现在让后端过滤；顺带删掉 `allExperiences` 与 `expName()` 本地查找 |
| `Home.vue` 删掉 `expName()`，改用 `g.experience_name` | 体验名由后端补全，前端不必再拿全量体验列表去查 |
| `Home.vue` 首页好物改为「按分类各取一款」 | 后端按产品编码升序返回，直接切前四条会得到三款茶加一款米，读起来像"某一类好物"。改成每个分类取第一款后，四张卡覆盖四个品类，且招牌的汉中仙毫仍在首位 |
| `types/index.ts` 给 `Experience` / `Product` 补 `poi_name` `experience_name` `category_code`，新增 `ProductCategory` | 与后端 VO 逐字对应 |

## 七、设计取舍（记录下来，避免以后重复讨论）

1. **数据包里产品写中文分类名，库里存分类编码。**
   数据包是给人维护的，写"茶叶"比记"CAT-TEA"更不容易错；但库里必须存编码，
   否则改一次分类名所有产品的分类引用就全断了。解析放在导入这一步，把"人可读"
   和"机器稳定"分开。代价是分类名成了隐式外键，所以解析不出来时直接报错，
   不允许静默落一条没有分类的产品。

2. **不提供 `/api/pois/{id}/products`。**
   它和 `/api/products?poi_id=xxx` 是同一份数据的两条入口，两处都要维护排序、
   过滤与名称补全，迟早会漂移。代价是详情页发 3 个请求而不是 1 个，换来的是
   M2 的数据不渗进 M1 的 `PoiDetailVO`。

3. **产品列表按产品编码升序，不按分类编码排序。**
   按分类编码排会让首页前四条落在 `CAT-CRAFT` 起头的分类上，招牌的汉中仙毫
   反而进不了首页。改成编码升序后，"数据包里的编号顺序就是展示顺序"，
   想调首页推荐哪几款，改数据包编号即可，不用动代码。

4. **`product_count` 用 Java 聚合而不是 SQL `group by`。**
   为的是让计数和 `/api/products` 的列表出自同一套过滤条件（同城 + 在售）。
   换 `group by` 就有两份 `where` 子句要同步维护，哪天列表加了"仅上架新品"，
   计数会先对不上。产品量级只有十几条，性能不是这里的约束。

5. **抽取 `VoUtils` 与 `NameResolver`。**
   前者统一"逗号分隔转数组""DECIMAL 转 Double"的口径，避免三个接口对同一列
   给出不同格式；后者把 id → 名称的批量补全收在一处，一次查询分发，
   不在循环里逐个 `selectById`。都是 M2 引入第二、第三个消费者之后才做的，
   没有提前抽象。
