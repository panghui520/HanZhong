## 一、模块职责边界

M6 完整规划包含「到访消费 + 离境复购」两条链。本轮只做**离境复购**这一条的用户可见闭环：

```
乡村好物（挑产地）→ 加入购物车 → 填收货信息 → 提交订单 → 运营标记发货
```

**本轮明确不做**（每一项都有理由，不是漏做）：

| 没做的东西 | 为什么不做 |
|---|---|
| 在线支付 | 需要真实支付通道才成立。摆一个点不动的「去支付」按钮，答辩时会被追问"支付状态怎么流转" |
| 物流单号 / 物流轨迹 | 同上。没有快递对接，单号填进去之后什么也不会发生 |
| 取消 / 退款 / 售后 | 依赖支付通道 |
| 扣减 `product.stock` | `product` 表带 `city_code`，每次启动被 `CityPackImporter` 重灌 —— 扣减会在重启后失效。"看起来生效、实际不持久"比不做更糟。见 `db/V5__m6_order.sql` 顶部 |
| 商品分类导航 / 搜索 / 店铺 | 见第四节「红线守住情况」 |
| 匿名购物车 | 匿名车要靠 Cookie/localStorage 认领，中途登录要处理"这车归谁"的合并问题；下单本来就必须登录，从加购就要求登录更省事 |
| 只结算勾选的几件 | 要前端传行 id、服务端再校验归属，多一层校验换"少买两件"的便利，不划算。要少买先在购物车里删 |
| 地址簿 | 见第三节「地址为什么做快照」 |
| 部分发货 / 拆单 | 一单一次发完 |

依赖关系：M6 依赖 M1（`poi` 提供产地名称）、M2（`product` / `experience`）、M8（登录态与角色）、M9（`PoiImage` / `SceneArt` 的图片位约定）。**M6 不被任何已验收模块依赖**，所以它可以独立迭代。

## 三、关键设计验证（都是实测，不是"应该没问题"）

### 1. 金额一律服务端重算（实测）

下单请求体里**故意塞** `total_amount: 0.01` 和一个伪造的 `items` 数组：

```json
{
  "receiver_name": "田泽晖", "receiver_phone": "13800000001",
  "receiver_address": "陕西省汉中市汉台区中山街 12 号 3 单元 501",
  "total_amount": 0.01,
  "items": [{ "product_id": "PRD-001", "unit_price": 0.01, "quantity": 1 }]
}
```

实测结果：成交金额 **1340.00**（= 库里 268 × 购物车里的 5 件），明细单价 **268**，前端传的 `0.01` 完全没被采纳。

> 这是电商类功能最经典的漏洞入口：只要前端能传单价，抓个包改成 0.01 就成交了。

### 2. 挂靠关系快照到订单行上（实测）

`order_item` 里存的不是"引用"，是**下单那一刻的值**：

```
experience_id = E-001   experience_name = 高山茶园采制一日
poi_id        = P-RUR-002   poi_name   = 南郑·黄官茶园
```

为什么必须这样，而不是靠 `product_id` 反查：产品以后下架、甚至被换城市的数据包清掉，历史订单仍然要说得清"这件东西来自哪次体验"。这是项目第一条红线（农产品必须挂靠体验或产地）在数据层的落实 —— 让"消费链延伸"成为**可核对的数据事实**，而不是一句宣传语。

用户可见的形态：购物车分组标题、订单行的锚点行、结算摘要的分组，三处都显示并**可点回详情**。

### 3. 地址为什么做快照（不建地址簿）

两个理由，第二个是决定性的：

1. 地址簿是"复购很多次"才划算的设计，本项目用户大概率只买一次；
2. **快照语义**：若订单引用地址簿的 id，用户后来改了收货地址，历史订单上显示的地址会跟着变 —— 那已经是错账了。

实测：下单后把订单读回来，`receiver_name` / `receiver_phone` / `receiver_address` / `remark` 都是提交时的值。

### 4. 购物车不存价格（实测）

`cart_item` 只有 `(user_id, product_id, quantity)`，没有单价列。购物车显示的是**当前价格**，价格只在下单那一刻快照进 `order_item`。所以产品调价后：购物车里的数字会变（正确），历史订单不会变（也正确）。

实测：加购后改数量，`subtotal` 由服务端按**当前**库价重算并回传。

### 5. 下单三步同成同败（代码约束）

`createOrder` 带 `@Transactional(rollbackFor = Exception.class)`，包住「建订单 → 建明细 → 清空购物车」。若明细写完、清车失败，用户会看到"购物车还在、订单也生成了"，重复下单概率极高。

清车刻意放在**最后**：万一上面任何一步抛异常，事务回滚时购物车还是原样，用户可以改一下再试。

实测：下单成功后 `GET /api/cart` 返回 `[]`，`GET /api/cart/count` 返回 `0`。

### 6. 库存只校验不扣减（实测）

超库存加购返回 `6004`，错误信息带上剩余数量（`「羌绣桌旗·收藏级」仅剩 40 件`）。**不写回 `product.stock`** —— 理由见第一节表格。

### 7. 越权一律按「不存在」处理（实测）

| 场景 | 返回 | 为什么不是 4003 |
|---|---|---|
| visitor2 改 visitor1 的购物车行 | `6002` | 4003 等于告诉对方"这一行确实存在"，可以被枚举 |
| visitor2 看 visitor1 的订单 | `6005` | 同上，不泄漏单号是否存在 |

### 8. 订单状态只有两个（实测）

`PENDING 待发货` → `SHIPPED 已发货`。中文状态名由服务端算（`status_label`），前端不维护映射表 —— 加一个状态就通知前端改一次，迟早漏掉某处显示成裸的英文枚举。

重复点「标记已发货」返回 `6006`，且**发货时间不会被第二次点击刷新**（实测比对过前后两次读到的值）。

### 9. 单号格式（实测）

`HY` + `yyyyMMddHHmmss` + 4 位随机，如 `HY202609251853041838`。不用自增主键当单号：让用户念一串连续数字既容易和别的系统撞号，也把"一共卖了多少单"暴露出去。

### 10. 探索页分类改版（实测，浏览器端 77 条断言）

**改版前的实测问题**（数出来的，不是感觉）：

| 业态 | 山水 | 人文 | 乡野 | 合计 |
|---|---|---|---|---|
| SCENIC | 12 | 6 | 0 | 18 |
| RURAL_SPOT | 0 | 0 | 12 | 12 |
| **FOOD** | **2** | **4** | **0** | **6** |
| **LODGING** | **3** | **1** | **0** | **4** |
| TRANSPORT | 0 | 2 | 0 | 2 |

餐饮只有 6 条、住宿只有 4 条，还被 3 个主题拆散 —— 切到「山水」只剩 2 条餐饮，切到「乡野」餐饮和住宿**都是 0**。用户想找吃的地方，得先猜它被归进了哪个主题，猜错就是空列表。

**改版后的信息架构**：

```
一级 = 类别    景区 18 / 乡村旅游 12 / 餐饮 6 / 住宿 4 / 交通 2   ← 条数来自真实数据
二级 = 主题    山水 / 人文 / 乡野（只列当前类别里真的有的，带条数，可取消）
三级 = 区县 + 关键词
```

- **刻意不做「全部」这一档**：混着看正是"一进来很乱"的来源。想看全局有页头四个数字。
- **类别可进 URL**（`?type=FOOD`），刷新和分享都停在同一类。
- **切类别会重置二三级筛选**，否则会出现"新类别 + 旧区县"的空结果，看着像页面坏了。
- 类别名取系统统一的 `BUSINESS_LABEL`，第一类显示**「景区」**而不是口语里的「景点」—— 详情页、卡片角标、管理端用的是同一套词汇，这一页另起名字会让用户以为不是一回事。
- 原页面底部的「乡村好物」4 张商品卡**移除**，改为一条指向 `/goods` 的入口带：商品有独立页了，在这一页再铺一遍会让层级变乱且与那一页重复。

## 四、红线守住情况

项目三条红线里的第一条是「**核心不是电商**，农产品必须挂靠 `experience_id` 或产地 `poi_id`，**不设独立商城页面**」。用户这次的要求是"农产品拆成独立页 + 电商式下单流程"，与这条红线在**形态**上有张力。处理方式：

| 要求 | 做法 | 守住红线的点 |
|---|---|---|
| 独立页面 | 页面标题是「**体验过的，可以带走**」，不是"商城首页" | 主张是消费链延伸，不是交易 |
| 商品浏览 | 筛选维度是**产地**，不是品类 | 品类（茶叶/粮油/腊味）是货架语言，会把产地信息抹平；而"洋县的米"值得买，正因为挂在一次具体体验上 |
| 商品卡 | 每张必须显示**产地 + 体验锚点**，产地可点回详情 | 让"消费链延伸"可核对 |
| 下单流程 | 挑 → 加购 → 填收货信息 → 提交 → 运营发货 | 下单本身是 M6 规划内的能力，不在红线上 |
| 不做 | 无店铺、无商家、无搜索、无商品分类导航、无支付、无物流 | 没有一处出现"旗舰店 / 商家 / 商品分类"这类货架文案（浏览器端断言实测） |

购物车的分组维度也是**「来自哪次体验」而不是按店铺** —— 普通电商按店铺分组是因为要拆单、要按商家算运费；这里没有商家，供货方就是乡村点本身。

## 六、踩过的坑（写下来避免重复）

### 1. `@RequestBody Map<String, String>` 会把客户端参数问题报成「服务内部错误」

**现象**：验收脚本给下单接口塞了一个 `items` 数组，返回 `code=9000 服务内部错误`。

**根因**：接口声明的是 `Map<String, String>`，Jackson 无法把数组转成 `String`，抛 `HttpMessageNotReadableException`，落到 `GlobalExceptionHandler` 的兜底分支报 9000。

**为什么这是个真问题**：9000 的意思是"服务端出故障了"，而实际情况是**客户端**发的东西不对。这个报错会把排查方向整个带偏（我自己就先怀疑了订单表结构和 `attachItems`，查了半页日志才发现问题在请求体解析）。

**修法两层**：

1. 接口改成 `Map<String, Object>`，只取自己认识的四个键，多传什么都不影响（`CartController` 早就是这个写法，`OrderController` 当时没跟上）；
2. `GlobalExceptionHandler` 新增两个 handler：`HttpMessageNotReadableException` → `1002 请求参数不合法`；`MethodArgumentTypeMismatchException` → `1002 参数不合法：xxx`（后者管的是 `/api/orders/abc` 这种路径变量不是数字的情况，原来也报 9000）。

### 2. 写接口返回内存对象 vs 回读数据库：同一个字段两次读不一致

**现象**：标记已发货后，接口返回的 `shipped_at` 是 `...18:45:08.7085987`；紧接着 `GET /api/orders/{id}` 读回来是 `...18:45:09`。**同一个字段，两次读到的值不一样。**

**根因**：Java 的 `LocalDateTime.now()` 带纳秒，而 `shipped_at` 列是 `DATETIME`（无小数秒），MySQL 会四舍五入。`shipOrder` 直接返回了内存里的对象，没回读。

**修法**：`shipOrder` 和 `createOrder` 都在写完之后**回读一次**再返回。这不只是"稳妥"，是"返回库里真实存了什么"而不是"我们以为写了什么"。

`createOrder` 同一个毛病还更明显：`created_at` 由数据库默认值 `CURRENT_TIMESTAMP` 生成，内存对象里是 `null` —— 不回读的话下单响应里 `created_at` 会**整个字段缺失**（全局 `non_null` 序列化），前端拿到的订单对象比列表接口少字段。

> 这和 M8 那条教训是同一类：「原子自增改完要回读一次拿真实值」。

### 3. 提示条是组件状态，一跳转就没了

**现象**：未登录点「加入购物车」，浏览器验收脚本抓到的提示是空字符串。

**根因**：`say('err', ...)` 之后立刻 `router.push('/login')`，Goods 组件当场卸载，提示条从来没渲染过。用户看到的是"点了按钮，莫名其妙到了登录页"。

**修法**：先提示，**0.8 秒后**再跳。0.8 秒足够读完一句"请先登录，再把它带回家"，又短到不显得卡顿。同时用一个 `leaving` 标记禁掉按钮，防止这 0.8 秒里被连点。

**验收脚本也要跟着改**：断言必须在跳转**之前**（0.8s 窗口内）抓提示，然后等跳转完成再断言 URL —— 这正是要验证的时序。

### 4. 单个「正在提交」锁会静默丢掉第二件商品

**现象**：连续点两件**不同**商品，只有第一件进了购物车，第二件毫无反应。

**根因**：用一个 `pending: string` 做单飞锁，第二个请求直接 `return`。

**修法**：改成按商品加锁（`pendingIds: string[]`），同一件商品连点仍然只加一次，不同商品互不影响。断言改成"连续点两件，角标 +2"。

### 5. 断言里的字符串匹配会把"否定的文案"当成肯定

**现象**：我写了 `check('页面上不出现「店铺」这种商城概念', !body.includes('店铺'))`，结果 FAIL —— 因为页面正文里有一句刻意的表态：「这里没有店铺，只有那几次你到访过的乡村」。

**教训**：用关键词否定来验证"没有某个概念"是不可靠的，文案里只要提一句就会被判失败。正确做法是列出**具体的货架文案**（旗舰店 / 商家 / 品牌馆 / 商品分类）去匹配，并把"显式声明没有店铺"单独作为一条**肯定**断言。

### 6. `SceneArt` 的 variant 是字面量联合类型，数据字段是 `string`

**现象**：三个新页面传 `p.scene` 编译不过 —— `Type 'string' is not assignable to type '"qinling" | ...`。

**修法**：抽出 `web/src/utils/scene.ts`，把 7 个变体与归一化函数 `sceneVariant()` 放在一处，`SceneArt` / `PoiImage` / 管理端下拉框 / 三个新页面共用。

**为什么不直接把 props 放宽成 `string`**：那样拼错的值会静默落到模板最后一个 `v-else` 分支，页面看着正常、**画错了场景**。本项目图片一律是手写 SVG、`web/public/` 是空的，没有实拍图能纠正这个印象，所以"画错场景"不是小瑕疵。宁可显式回落到一个默认变体。

顺带把 `PoiImage` 里原来的 `props.scene as Variant` 硬转也换成了 `sceneVariant()` —— 硬转在遇到非法值时同样是静默画错。

## 七、已知限制与后续扩展点

| 限制 | 后续怎么做 |
|---|---|
| 不扣库存 | 真正的库存账需要一张**不带 `city_code`** 的流水表（如 `product_stock_ledger`），用「入库 - 出库」求和得到可用量。这样既不随重启消失，也能追溯每一次扣减 |
| 无支付 | 接入支付通道后，`orders` 加 `PAID / CANCELLED` 状态，`status_label` 跟着扩展（服务端算的，前端不用改） |
| 无物流单号 | 加 `tracking_no` 列 + 运营端一个输入框，`SHIPPED` 之后再挂一个「已签收」 |
| 无地址簿 | 需要时加 `user_address` 表，但**订单行上的地址快照要保留**，不能改成引用 |
| 无匿名购物车 | 需要时在 Cookie 里放 `cart_token`，登录时做一次合并（同商品数量相加），要处理"合并到哪一辆车"的冲突 |
| 订单列表无分页 | 当前量级（个位数）不需要。加 `LIMIT/OFFSET` + 总数即可，注意保持"待发货优先"的排序语义 |
| `?type=` 只在探索页 | 探索页其他筛选（主题/区县/关键词）暂不进 URL，避免每次输入都改 history |
| 农产品页无搜索 | 16 款商品用不上搜索；超过 30 款再加，且筛选维度仍建议保持"产地" |

## 八、结论

M6 的离境复购闭环（挑产地 → 加购 → 结算 → 下单 → 运营发货）**功能完整、后端 65 项 + 前端 77 项断言全部通过**，七个既有页面回归无异常，红线未破。

两处本轮修掉的真问题值得单独记住：

1. **参数解析失败被报成「服务内部错误」** —— 报错方向性错误比不报错更费时间；
2. **写接口返回内存对象导致同一字段两次读不一致** —— 写完之后回读一次。

下一模块建议做 **M4 行程规划**（`Itinerary.vue` 目前是前端用 citypack + `capacityUsage` 现算的，正是 M4 要替换的），或 **M5 承载力与分流**（探索页上的承载率目前来自 `mock/stats.ts`，是 M5 要替换的）。
