# M8 认证与权限 · 验收记录

> 验收日期：2026-09-24 · 结论：**通过（后端部分）**
> 模块范围：`db/V3__m8_auth.sql` → Spring Security + JWT 后端 → curl 全链路验收
> 本轮**只覆盖后端**；前端认证接入与三个页面的视觉升级是后续阶段，不在本记录范围。

## 一、模块职责边界

**做**：邮箱验证码注册、邮箱密码登录、JWT 签发与校验、`token_version` 服务端失效、
游客/运营角色区分、把 M1/M2/M3 已有公开接口显式放行。

**不做**：第三方登录（微信/GitHub）、找回密码、修改邮箱、用户资料编辑、运营端人事管理。
这些都不在 M8 的目标里——M8 要解决的是"现在谁都能进"这一个问题。

**为什么 M8 独立编号而不并入某个纵切模块**：认证是**横切关注点**，M1–M7 每个模块都要用到它，
但它不属于任何一个。把它塞进 M1 会让 M1 的职责变成"资源 + 认证"两件事；
单独立号后，后续所有模块只需在 `SecurityConfig` 的白名单里加一行。

**一条不可违反的边界**：认证表**不带 `city_code`**。
`CityPackImporter` 每次启动按 `city_code` 删除并重灌业务表，
`app_user` 与 `auth_email_code` 只要不挂 `city_code`，就永远不会被导入器碰。
这不是巧合，是设计——本轮已实测验证（见「四、关键设计验证」第 1 条）。

## 四、关键设计验证

### 1. 认证表不被 CityPack 重灌清空（实测）

`CityPackImporter` 是 `ApplicationRunner`，每次启动全量删除并重灌业务表。
启动日志：

```
[CityPack] 导入完成 city=hanzhong 资源点=42 关系=275 分类=10 体验=14 产品=16
```

重灌后 `app_user` 与 `auth_email_code` 数据仍在（`auth_email_code` 保留了上一轮运行的记录），
证明"认证表不带 `city_code` → 永不被导入器碰"这条设计假设成立。

### 2. token_version 服务端失效（实测）

| 步骤 | 数据库 `token_version` | 原令牌访问 `/api/me` |
|---|---|---|
| 注册后 | 0 | `code=0`（成功） |
| 调用 `/api/me/logout` | 1 | `code=4001`（失败） |

JWT 天生无状态，签发后到期前一直有效，改密码/退出登录都拦不住它。
把版本号写进 claims（`ver`），每次校验比对库里的值，退出时 +1 即让该用户**全部**历史令牌立即失效。
比维护"已失效令牌黑名单"简单，且不会无限增长。

### 3. 验证码五道闸（实测）

| 闸 | 机制 | 实测结果 |
|---|---|---|
| ① 发送冷却 60 秒 | `createdAt + cooldownSeconds` | 重复发送返回 `4103` |
| ② 有效期 5 分钟 | `expiresAt` | 校验时 `isAfter(expiresAt)` 即 `4105` |
| ③ 错误次数上限 5 次 | `attempt_count` 原子自增 | 逐次返回剩余 4/3/2/1，第 5 次 `4107`，`attempt_count=5`、`invalidated_at` 已写 |
| ④ 一次性 | `used_at` | 同一码二次使用返回 `4102`（已注册）/ `4106`（已使用） |
| ⑤ 同时只有一条有效码 | 发新码时作废旧码 | 旧码因错误超限后返回 `4107` |

### 4. 验证码哈希用固定盐 SHA-256 而非 BCrypt

BCrypt 每次加盐不同，就无法用 `code_hash` 做等值查询，只能全表扫出来逐个比对。
验证码只有 6 位数字，本来就不是抗离线爆破的强度，**真正的防线是闸 ①②③**。
比对用 `MessageDigest.isEqual`（按字节恒定耗时），避免"前几位对没对"的时间差泄漏。

### 5. 角色从数据库读而非从 JWT claims 读

避免"用户被降权后旧令牌仍带旧角色"的时间窗。
`JwtAuthFilter` 每次用 `sub`（userId）回库查当前角色，令牌里的 `role` claim 只作参考不作依据。

### 6. 认证失败也返回 HTTP 200

`AuthJsonHandlers` 同时实现 `AuthenticationEntryPoint` 与 `AccessDeniedHandler`，
一律 `setStatus(SC_OK)` + `Result`（`4001` 未登录 / `4003` 无权限）。
这是沿用本项目"HTTP 恒 200、看 body.code"的约定，不是疏忽。

## 六、本轮修掉的两个真实缺陷

### 缺陷 1：错误次数完全不累加，闸 3 形同虚设（第一次修复未彻底）

**现象**：连错 5 次，每次提示都是"还可尝试 4 次"；`auth_email_code.attempt_count` 恒为 0。
SQL 日志显示 `UPDATE auth_email_code SET attempt_count=? WHERE id=?` **执行了且报告 `Updates: 1`**，
参数恒为 `1(Integer)`。

**根因（第一层）**：`AuthService.register` 带 `@Transactional`，
它调用 `verifyCode` 失败时抛 `BizException` → **整个注册事务回滚**，
把同事务里刚做的 `attempt_count` 自增一并抹掉。

**第一次修复及为何无效**：把自增抽到 `@Transactional(propagation = REQUIRES_NEW)` 的 `recordFailure`，
期望它独立提交。日志显示新事务确实开了，但**计数依然丢**。

**真正的根因（第二层）**：Spring 的 `REQUIRES_NEW` 只是**挂起**外层事务，
内层事务向连接池要连接时，拿到的**还是外层事务正占着的那条物理连接**
（挂起不等于归还）。MySQL 一条连接同一时刻只有一个事务作用域，
于是这条 UPDATE 实际仍跑在外层事务里，外层一回滚，计数照样被抹掉。
日志里的证据：内层与外层打印的 `ConnectionImpl@2d73e8c4` 是同一个对象。

**最终修复**：不再依赖事务传播，改为**调整调用顺序让校验发生在事务开启之前**：

```
register()                          ← 刻意不加 @Transactional
  ├─ 1. 校验邮箱/密码/查重            （只读，无需事务）
  ├─ 2. codeService.verifyCode(...)  ← 事务外，一次 UPDATE 即一次提交
  └─ 3. doRegister(...)              ← @Transactional，包住"建用户 + 消耗验证码"
```

同时把自增改成数据库原子操作 `SET attempt_count = attempt_count + 1`，
并在注释里写明"REQUIRES_NEW 为什么在这里不成立"——这是最容易重复踩的坑。

### 缺陷 2：demo 渠道验证码 grep 不到（Windows GBK 代码页）

**现象**：日志里明明有验证码，验收脚本却提取失败。

**根因**：日志文件落盘是 **GBK 字节**（Windows 控制台代码页），
脚本按 UTF-8 匹配中文标签「验证码」必然失配。

**修复**：不只修脚本，而是**从源头消除对编码的依赖**——
在 `DemoCodeSender` 里加一行**纯 ASCII 机器可读契约**：

```
AUTH_CODE email=<邮箱> code=<验证码> ttl=<分钟>
```

并注明「改动这一行务必同步更新 auth-acceptance.sh 的抽取正则」。
脚本改用 `grep -a "AUTH_CODE"` + `sed 's/.*code=\([0-9]\{4,\}\).*/\1/p'`（不写死 6 位，位数由配置决定）。

### 附带修掉的验收脚本自身 3 个 bug

| 现象 | 根因 | 修复 |
|---|---|---|
| `GET /api/city` 明明是 `{"code":0}` 却报失败 | `head -c 400` 按**字节**截断，把中文字符劈成两半，sed 输出尾部挂上无效字节，`"0"` 变成 `"0<乱码>"` | 去掉字节截断，改用 `^` 行首锚定（足以避开 data 里嵌套的 `"code"` 键） |
| `GET /api/pois/P-SCE-001` 同上 | 同上 | 同上 |
| `GET /api/ai/health` 报 `code=3001` 当作回归 | Python 服务未启动时的**设计降级**被误判 | 新增 `assert_reachable()`，接受 `0|3001|3002` |

## 七、已知问题与待办

### 1. `application.yml` 的 `server.port: 8080` 在启动时被覆盖为 61028（**未修，已定位**）

**现象**：yml 明确写 `server.port: 8080`，`target/classes/application.yml` 内容也正确，
但启动日志是 `Tomcat initialized with port 61028`，随后 `Port 61028 was already in use` 启动失败。

**已排除**：
- 无 `SERVER_PORT` / `PORT` / `SPRING_APPLICATION_JSON` / `JAVA_TOOL_OPTIONS` 等环境变量（`env | grep` 实测为空）
- 无 `.env`、无 `application-*.yml`、无 `.mvn/jvm.config`、无 `~/.m2/settings.xml`、pom 里无端口配置
- 未激活任何 profile（日志：`No active profile set`）
- yml 里**其他配置项均正常生效**（`citypack-dir: ../citypack` 解析正确、数据源连上了 `hanyou_brain`），
  说明**不是 YAML 没被读取**，而是 `server.port` 这一项被更高优先级的属性源覆盖

**关键实验**：

| 启动方式 | Tomcat 实际端口 |
|---|---|
| 不带参数 | **61028**（失败） |
| `--server.port=19999` | 19999（成功） |
| `--server.port=`（显式空值） | **8080**（成功，且连续 3 次稳定） |

**已定位的部分**：61028 是 **WorkBuddyAI 自身**在监听的本地端口
（`Get-NetTCPConnection` 实测：`PID 16072 : WorkBuddyAI : D:\developTools\AiTool\WorkBuddyAI\WorkBuddyAI.exe`）。
用 Java 直接测绑定能力也确认：`bind 8080 OK` / `bind 61028 FAILED: Address already in use`。

**当前判断**：这是 **IDE 沙箱在 fork Java 子进程时注入的端口属性**，属性源优先级高于 YAML，
且不通过环境变量（否则 `env` 会看到）传递——很可能走 fork 时的 JVM 系统属性或 IDE 侧包装。
